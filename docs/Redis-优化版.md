# Redis 面试八股文（优化版）

---

## 一、基础与数据结构

---

### 1.1 核心特性

---

#### 1. Redis 为什么这么快 / Redis 高性能怎么实现的？ (高)

1.  **纯内存操作**
    绝大部分读写操作直接在内存中完成，无磁盘 I/O 瓶颈。

2.  **单线程模型（核心命令处理）**
    6.0 以前网络 I/O 和命令执行全部由单线程完成，避免多线程锁竞争、上下文切换开销。6.0 后引入多线程 I/O 处理，但命令执行仍为单线程，保证原子性。

3.  **高效的数据结构**
    每种数据类型都有专门优化的内部编码（如 String 的 SDS，List 的 Quicklist，ZSet 的跳表+字典），时间和空间复杂度低。

4.  **I/O 多路复用**
    采用 epoll/kqueue 等机制，单线程能同时监听大量客户端连接，轮询处理就绪的 I/O 事件，吞吐量极高。

5.  **简单的 RESP 协议**
    文本协议解析开销极低，命令交互轻量。

---

#### 2. 本地缓存和 Redis 缓存的区别，优缺点？ (低)

| 对比点 | 本地缓存（如 Caffeine、Guava） | Redis 缓存 |
| --- | --- | --- |
| 存储位置 | JVM 堆内 / 堆外内存 | 独立进程，远程服务器 |
| 访问速度 | 微秒级，无网络开销 | 毫秒级，有网络 RTT |
| 容量限制 | 受单机内存限制 | 可集群扩展，存储更大 |
| 数据共享 | 单个服务实例独享 | 多服务实例共享一致缓存 |
| 可用性 | 随服务宕机丢失、重启即失效 | 独立部署，支持持久化，高可用 |
| 一致性 | 无网络延迟，天然强一致 | 分布式需考虑缓存一致性策略 |
| 优点 | 极致速度，无网络依赖 | 数据共享、容量大、高可用、功能丰富 |
| 缺点 | 容量小，不可共享，无法持久化 | 增加网络开销，需额外维护 |

---

### 1.2 数据类型与底层

---

#### 1. Redis 常用的数据结构有哪些？ (高)

Redis 基础数据结构有 5 种，以及 3 种扩展结构：
*   **基础**：String（字符串）、List（列表）、Set（集合）、ZSet（有序集合）、Hash（哈希）
*   **扩展**：HyperLogLog（基数统计）、Geo（地理位置）、Stream（消息流，5.0+）
*   此外还有 Bitmap、Bitfield 等基于 String 的位操作。

---

#### 2. Redis 每种数据类型的使用场景 (高)

*   **String**
    缓存对象、计数器（`INCR`）、分布式锁（`SETNX`）、Session 共享。
*   **Hash**
    存储对象属性（用户信息、商品详情），可针对单个字段读写，节省内存。
*   **List**
    消息队列（`LPUSH`/`BRPOP`）、最新动态列表、栈/队列。
*   **Set**
    标签系统、好友关系（共同关注、交集并集）、抽奖去重、点赞用户集合。
*   **ZSet**
    排行榜、延迟队列（按时间戳排序）、带权重的任务调度。
*   **HyperLogLog**
    海量 UV 统计，占用极小内存（12KB）。
*   **Geo**
    附近的人、地理位置检索。
*   **Stream**
    持久化、多消费者组的消息队列，可作为轻量 MQ。

---

#### 3. String 底层结构 (中)

Redis String 的底层编码有三种，根据存储内容和长度自动切换：
1.  **INT**：整数值（如计数器），直接存储为 `long` 型，无额外结构。
2.  **EMBSTR**：短字符串（≤44 字节），采用紧凑型 SDS（Simple Dynamic String），字符串与 RedisObject 连续分配内存，一次分配一次释放，节省开销。
3.  **RAW**：长字符串（>44 字节），SDS 与 RedisObject 分离存储，需要两次内存分配。

SDS 对比 C 字符串优势：O(1) 获取长度、杜绝缓冲区溢出、二进制安全、减少内存重分配（预分配与惰性回收）。

---

#### 4. ZSet 底层的数据结构？ (中)

ZSet 根据元素数量和成员大小，有两种编码：
*   **压缩列表（listpack / ziplist）**：元素数量少且成员较短时使用，节省内存。
*   **跳表（skiplist）+ 字典（dict）**：元素较多时使用。
    *   跳表：维护元素按分值有序，支持范围查询、排序。
    *   字典：存储成员到分值的映射，O(1) 查询分值。
    *   两者共享相同元素对象指针，不浪费内存。

---

#### 5. 介绍一下跳表 (中)

跳表是一种有序数据结构，通过对链表添加多级索引实现快速查找：
*   最底层是一个包含所有元素的有序双向链表。
*   向上随机选取一些元素建立多级索引层，索引节点包含指向同层下一个节点的指针和指向下一层的指针。
*   查找时从顶层索引开始，快速跳过大量节点，逐步降至底层，平均时间复杂度 O(logN)，与平衡树相当。
*   实现简单，插入、删除仅需局部修改，无需像红黑树全局再平衡，非常适合范围查询，是 Redis ZSet 的核心结构。

---

### 1.3 应用场景实战

---

#### 1. Redis 的常见应用场景 / 你平时会用 Redis 做什么 (中)

*   缓存：热点数据、数据库查询结果、页面片段。
*   分布式锁：`SET key value NX PX` 实现互斥锁，Redisson 提供可重入锁。
*   计数器/限流：`INCR` 做点赞计数、API 调用限速（滑动窗口或令牌桶）。
*   排行榜：ZSet 存储分数，实时排名。
*   消息队列：List 阻塞读、Stream 消费组实现轻量异步队列。
*   共同好友/推荐：Set 的交并差实现关系计算。
*   Session 共享：集中式 Session 管理。
*   分布式 ID 生成：`INCR`/`INCRBY` 生成连续 ID。
*   地理位置：GEO 存储坐标，查询附近的人。

---

#### 2. 如何实现排行榜？ (中)

使用 **ZSet（有序集合）**，成员为用户 ID，分值为排行依据（如分数、时间）。
*   **更新分数**：`ZADD key score member`（覆盖式更新）。
*   **查询排名**：
    *   正序排名（分数从低到高）：`ZRANK key member`。
    *   倒序排名（分数从高到低，常用）：`ZREVRANK key member`。
*   **获取 Top N**：`ZREVRANGE key 0 N-1 WITHSCORES`。
*   **实时榜单**：直接查 ZSet。
*   **历史榜单**：定时将当日/当周 ZSet 持久化到 DB 或归档。
    若需同分按时间排序，可将分值设计为 `分数 + 时间戳小数`（如 `score.timestamp`）或额外维护二级排序。

---

#### 3. 实现简单的抽奖系统怎么做？ (中)

*   **使用 Set 去重抽奖**：
    参与用户放入 Set（`SADD`），抽奖时 `SRANDMEMBER`（可重复）或 `SPOP`（取走不重复）。
*   **使用 ZSet 按权重抽奖**（适合概率不同的抽奖）：
    每个奖品一个 ZSet，成员为用户，分值为随机数或权重，配合 `ZRANGE` 抽奖。
*   **List 随机抽奖**：
    用户压入 List，`LRANGE` 随机索引或 `LPOP` 模拟抽走。
*   **原子抽奖并记录**：用 Lua 脚本保证抽奖、减库存、记录中奖原子性。

示例（Set 不重复抽奖）：
```
SADD lottery:round1 user1 user2 ...
SPOP lottery:round1 3   // 抽出3个不重复中奖者
```

---

#### 4. 统计活跃用户怎么做？ (中)

*   **日活（DAU）**：使用 **Set**，Key 如 `active:20260622`，活跃即 `SADD`，通过 `SCARD` 统计。
*   **周活/月活**：
    *   方法 1：每日一个 Set，求并集（`SUNIONSTORE`）存入结果 Set 再计数。
    *   方法 2：使用 **Bitmap**，每个用户一个 bit，每天一个 Bitmap。`SETBIT user:login:20260622 uid 1`，日活用 `BITCOUNT`，周活/月活用 `BITOP OR` 合并后 `BITCOUNT`，内存极省。
*   **连续活跃**：Bitmap 做 `BITOP AND` 即可得到连续登录用户。

---

#### 5. 统计页面 UV 怎么做 (中)

*   **精确统计**：用 **Set** 或 **Bitmap**，UV 按天去重。
    *   `SADD uv:page:20260622 user_id`
    *   `BITFIELD` 或 `SETBIT uv:page:20260622 hash(user_id) 1`
*   **超大流量近似统计**：使用 **HyperLogLog**。
    *   `PFADD uv:page:20260622 user_id`（去重），`PFCOUNT` 直接获取 UV，12KB 内存可统计 2^64 个元素，误差 0.81%。
    *   可合并多天 `PFMERGE` 得到周/月 UV。

---

#### 6. 实现在线用户列表怎么做：按登录时间排序、可查询、踢人 (中)

**核心：ZSet 存储在线用户**，member=用户 ID，score=登录时间戳（或最后活跃时间）。
*   **登录**：`ZADD online_users <timestamp> <user_id>`
*   **按登录时间排序**：`ZRANGE`（升序）或 `ZREVRANGE`（降序）按时间先后获取。
*   **查询某用户是否在线**：`ZSCORE online_users user_id`，不为空则在线。
*   **查询指定时间段登录的用户**：`ZRANGEBYSCORE online_users min max`
*   **定时清理超时用户**：定时任务执行 `ZREMRANGEBYSCORE online_users 0 (now - timeout)` 移除不活跃用户。
*   **踢人**：`ZREM online_users user_id`，同时可向用户频道发布踢出消息（如 Pub/Sub 或 WebSocket 通知）强制下线。

---

#### 7. 不支持多端登录如何查询 (中)

同一账号只允许一个设备在线，存储账号到单一 token/设备映射。
*   使用 **Hash** 或 **String**：`HSET online_user_detail user_id token "<token>" device "<device_id>"`
*   查询某账号是否在线：`HEXISTS online_user_detail user_id` 或 `EXISTS user:online:<user_id>`
*   登录时覆盖之前信息，旧端通过心跳检测或通知使其失效。

---

#### 8. 支持多端登录如何查询 (中)

同一账号允许多设备，需要存储设备列表。
*   使用 **ZSet**（按登录时间）或 **Set**（无序）：
    *   `ZADD user:devices:<user_id> <login_time> <device_id>`
    *   查询账号在线设备列表：`ZRANGE user:devices:<user_id> 0 -1 WITHSCORES`
    *   查询总在线设备数：`ZCARD user:devices:<user_id>`
*   查询某设备是否在线：`ZSCORE user:devices:<user_id> <device_id>`

---

#### 9. 不支持多端登录如何踢人 (中)

*   由于仅存储单一映射，直接删除该账号的在线状态：`DEL user:online:<user_id>` 或 `HDEL online_user_detail user_id`
*   若旧设备持有长连接，可通过消息通道（如 Redis Pub/Sub `publish kick_channel user_id:device_id`）通知该设备下线。
*   踢人后需防止重连，可配合一个黑名单 Set 或 Token 失效机制实现强制退出。

---

#### 10. 支持多端登录如何踢人 (中)

需指定踢出具体设备。
*   踢出指定设备：`ZREM user:devices:<user_id> <device_id>`，并发送通知。
*   踢出全部设备：`DEL user:devices:<user_id>`
*   如果存在全局在线列表（所有在线用户大集合），踢出全部设备时还需从全局 Set/ZSet 中移除对应用户及其所有设备（若全局是按 user 存储则移除 user，若按 device 存储则需移除此用户关联的所有 device 项）。可通过 Lua 脚本保证原子性：
    ```
    local devices = redis.call('ZRANGE', KEYS[1], 0, -1)
    for _, device in ipairs(devices) do
        redis.call('ZREM', KEYS[2], device)
    end
    redis.call('DEL', KEYS[1])
    ```

## 二、线程模型与持久化

---

### 2.1 线程模型

---

#### 1. Redis 为什么设计成单线程的 (中)

1.  **CPU 不是瓶颈**
    Redis 是基于内存的操作，绝大部分请求处理时间极短（微秒级），性能瓶颈通常在内存大小或网络 I/O，而非 CPU 运算能力。

2.  **避免并发开销**
    单线程模型天然避免了多线程中的锁竞争、上下文切换、死锁等问题，极大降低了系统复杂度，使代码简洁易维护。

3.  **I/O 多路复用**
    采用 epoll/kqueue/select 等机制，单线程可以同时监听大量客户端连接，以事件驱动方式高效处理并发请求，吞吐量可达每秒十万级。

4.  **数据操作的原子性保证**
    单线程执行命令，天然保证每个命令的原子性，无需额外加锁，简化了事务和 Lua 脚本的实现。

---

#### 2. Redis 一定是单线程的吗 (中)

**不是**。Redis 整体是多线程的，但**核心命令执行一直是单线程**，具体演进如下：

*   **持久化和后台任务**：早期版本已有后台线程执行 `BGSAVE`、`AOF rewrite` 等操作，避免阻塞主线程。
*   **Redis 4.0 异步删除**：引入 `UNLINK`、`FLUSHALL ASYNC` 等命令，由后台线程异步释放大对象内存，防止 `DEL` 大 key 卡住主线程。
*   **Redis 6.0 多线程 I/O**：默认关闭，可配置开启。网络数据的读写、协议解析可由多个 I/O 线程并行处理，但**命令执行仍在主线程**，保持原子性和无锁特性。
*   **其他后台线程**：如 `bio_close_file`、`bio_aof_fsync` 等，处理关闭文件描述符、AOF 刷盘等任务。

因此，准确说法是：**Redis 核心命令执行是单线程的，但自 4.0 起支持多线程异步操作，6.0 起支持多线程网络 I/O**。

---

#### 3. Redis 6.0 之后为什么引入了多线程？ (中)

引入多线程 I/O 是为了**突破单线程网络读写的性能瓶颈**：

1.  **网络 I/O 成为新瓶颈**
    随着硬件发展（万兆网卡、多核 CPU），单线程处理大量网络数据读写和协议解析开始耗费大量 CPU，无法充分利用多核资源，成为吞吐量上限。

2.  **多线程分担 I/O 负载**
    将客户端连接的读事件、写事件的协议解析交给多个 I/O 线程并行处理，主线程只需执行命令，然后再由 I/O 线程写回响应。这样将原来串行的"读→执行→写"流水线化，整体吞吐量可提升近一倍。

3.  **保持命令执行的单线程**
    命令执行仍在主线程顺序处理，避免锁竞争，保证原子性和事务语义不变。I/O 线程只处理网络读写和协议解析，不触及数据状态。

4.  **开启建议**
    默认关闭，需在配置文件中设置 `io-threads` 及 `io-threads-do-reads yes`。通常只在 CPU 核心多且确实存在网络 I/O 瓶颈时开启，一般 4 核以下开启提升不明显。

### 2.2 持久化

---

#### 1. Redis 持久化机制（总述） (高)

Redis 提供三种持久化方式：**RDB**（快照）、**AOF**（追加日志）、**混合持久化**（4.0+）。

---

#### 2. RDB（Redis DataBase） (高)

*   **原理**：在指定时间间隔或手动触发时，生成某一时刻的数据快照（内存数据全量写入磁盘压缩二进制文件）。
*   **触发方式**：
    *   自动：`save <seconds> <changes>` 配置满足条件时自动执行 `BGSAVE`。
    *   手动：`SAVE`（阻塞主线程）/ `BGSAVE`（fork 子进程写入）。
*   **优点**：文件紧凑，适合备份和灾难恢复；恢复大数据集速度比 AOF 快；子进程持久化不阻塞主线程。
*   **缺点**：非实时持久化，两次快照间的数据可能丢失；fork 子进程时内存占用翻倍，大数据集下可能卡顿。

---

#### 3. AOF（Append Only File） (高)

*   **原理**：以日志形式记录每一个写操作，重启时通过重放命令恢复数据。
*   **同步策略**：
    *   `appendfsync always`：每条命令都同步刷盘，最安全但性能最低。
    *   `everysec`：每秒刷一次盘，平衡性能和安全（默认，最多丢失 1 秒数据）。
    *   `no`：由操作系统决定刷盘时机，性能最好但最不安全。
*   **AOF 重写**：当文件膨胀时，`BGREWRITEAOF` 通过子进程分析当前数据生成最简命令集，压缩 AOF 体积，异步进行。
*   **优点**：持久化更实时，丢失数据少；文件可读可编辑；自动重写控制体积。
*   **缺点**：同数据量下 AOF 文件通常比 RDB 大；恢复速度比 RDB 慢。

---

#### 4. 混合持久化（4.0+） (高)

*   **原理**：结合 RDB 与 AOF，`aof-use-rdb-preamble yes` 开启后，AOF 重写时先将当前数据以 RDB 格式写入 AOF 文件前半部分，后续的增量写入以 AOF 命令追加到文件末尾。
*   **优点**：兼具 RDB 恢复快和 AOF 数据丢失少的优点。
*   **缺点**：文件结构稍复杂，不能像纯 AOF 那样完全可读；向下兼容性需注意。

通常线上推荐使用 **混合持久化 + `appendfsync everysec`** 达到安全与性能平衡。

## 三、过期淘汰与缓存策略

---

### 3.1 过期与淘汰

---

#### 1. Redis 的过期策略 (高)

Redis 采用 **惰性删除 + 定期删除** 的组合策略：

1.  **惰性删除**
    *   当客户端访问某个 Key 时，先检查是否过期，过期则立即删除并返回空。
    *   优点：对 CPU 友好，只在访问时处理。
    *   缺点：若大量过期 Key 一直不被访问，会占用内存不释放。

2.  **定期删除**
    *   Redis 内部每 100ms（默认 `hz 10`）会随机抽取一部分设置过期的 Key，检查并删除其中已过期的 Key。
    *   通过限制执行时长和频率，避免长时间阻塞。
    *   若一次抽查中过期 Key 占比超过 25%，则继续循环抽样，防止大量过期 Key 堆积。

二者结合，平衡 CPU 和内存的消耗。

---

#### 2. 为什么 Key 过期不立即删除？ (高)

*   **CPU 开销过大**
    若为每个 Key 设置精确的定时器，海量 Key 时将产生大量定时事件，CPU 需要不断扫描、处理过期，严重影响性能。
*   **Redis 单线程模型**
    过期处理在主线程执行，如果立即删除大量 Key，会长时间阻塞正常请求。
*   **折中设计**
    采用惰性+定期删除，将删除操作分摊到访问触发和后台抽样中，既保证内存不会无限增长，又避免 CPU 突刺。

---

#### 3. 内存淘汰机制 (高)

当 Redis 内存超出 `maxmemory` 限制时，根据配置的淘汰策略对 Key 进行驱逐：

| 策略 | 说明 |
| --- | --- |
| `noeviction` | 不淘汰，写入操作返回错误（默认） |
| `allkeys-lru` | 在所有 Key 中，淘汰最近最少使用的 |
| `volatile-lru` | 在设置了过期时间的 Key 中，淘汰最近最少使用的 |
| `allkeys-lfu` | 在所有 Key 中，淘汰最不经常使用的（4.0+） |
| `volatile-lfu` | 在设置了过期时间的 Key 中，淘汰最不经常使用的（4.0+） |
| `allkeys-random` | 在所有 Key 中，随机淘汰 |
| `volatile-random` | 在设置了过期时间的 Key 中，随机淘汰 |
| `volatile-ttl` | 在设置了过期时间的 Key 中，淘汰剩余存活时间最短的 |

**LRU 与 LFU 区别**：LRU 关注最近一次访问时间；LFU 关注访问频率，更能避免偶发性访问导致热点数据被误淘汰。

---

### 3.2 缓存三大问题

---

#### 1. 缓存击穿 (高)

*   **定义**：一个热点 Key 在缓存过期的瞬间，大量并发请求同时访问该 Key，穿透缓存直接打到数据库，导致数据库瞬时压力过大。
*   **解决方案**：
    1.  **互斥锁**：查询缓存未命中后，通过分布式锁（如 Redis `SETNX`）控制仅一个线程回源加载数据并写入缓存，其余线程等待或返回旧值。
    2.  **逻辑过期**：缓存不设置物理过期时间，在值中存储逻辑过期时间。获取时若逻辑过期，返回旧值同时异步更新缓存，保证高可用。
    3.  **永不过期**：对极热点 Key 不设置过期时间，通过后台任务主动刷新。

---

#### 2. 缓存穿透 (高)

*   **定义**：查询一个数据库和缓存中都不存在的数据（如恶意构造不存在的 ID），每次请求直接打到数据库，缓存形同虚设。
*   **解决方案**：
    1.  **布隆过滤器**：将所有可能存在的数据哈希到足够大的 bitmap 中，查询前先判断 Key 是否存在，不存在则直接拦截返回。
    2.  **缓存空值**：对查询不到的 Key，缓存一个空值或特殊标记，设置较短过期时间，防止重复查询。
    3.  **参数校验**：在业务层做基本合法性校验，过滤明显非法的请求。

---

#### 3. 缓存雪崩 (高)

*   **定义**：大量缓存 Key 在同一时间段集中过期，或 Redis 服务宕机，导致所有请求直接落到数据库，造成数据库崩溃。
*   **解决方案**：
    1.  **过期时间加随机值**：在基础过期时间上增加随机偏移，避免集中过期。
    2.  **高可用架构**：Redis 使用主从+哨兵或集群模式，保证缓存层高可用。
    3.  **限流与熔断**：对数据库访问进行限流，或当检测到缓存不可用时触发熔断保护。
    4.  **多级缓存**：本地缓存 + Redis 缓存组合，Redis 不可用时仍有本地缓存兜底。

---

#### 4. 缓存预热 (中)

*   **定义**：系统上线或重启后，提前将热点数据加载到缓存中，避免上线瞬间大量请求直接穿透到数据库。
*   **方案**：
    1.  系统启动时运行预热脚本，批量加载热点数据。
    2.  通过后台定时任务定期刷新缓存中的热点数据。

---

### 3.3 缓存读写策略

---

#### 1. 缓存读写策略概述 (高)

常见三种策略：**Cache Aside**（旁路缓存）、**Read/Write Through**（读写穿透）、**Write Back**（写回）。

---

#### 2. Cache Aside（旁路缓存）策略 (高)

最常用的缓存模式：
*   **读**：先查缓存，命中则返回；未命中则查数据库，将结果写入缓存后返回。
*   **写**：先更新数据库，再删除缓存（或更新缓存）。
*   **适用**：大部分业务场景，实现简单，读多写少场景最佳。

---

#### 3. Read/Write Through（读穿 / 写穿）策略 (中)

*   **读穿**：缓存不命中时，由缓存服务自动从数据库加载数据并写入缓存，应用层只与缓存交互。
*   **写穿**：写入时缓存服务自动将数据同步写入数据库后才返回成功。
*   **特点**：应用层完全不用关心数据库，但缓存服务需具备读写数据库的能力（如 Redis + 自定义 CacheLoader）。

---

#### 4. Write Back（写回）策略 (中)

*   **原理**：写入时仅更新缓存，标记为脏数据。缓存服务异步批量将脏数据写回数据库。
*   **优点**：写入性能极高，适合写多读少的场景。
*   **缺点**：存在数据丢失风险（缓存宕机导致脏数据未回写），一致性弱。

---

### 3.4 缓存一致性

---

#### 1. 缓存与数据库一致性的问题 (高)

一致性问题是分布式系统中缓存更新与数据库写操作非原子导致的，典型场景：
*   **先删缓存再更新 DB**：A 删缓存，B 读未命中回源旧值写入缓存，A 更新 DB → 缓存中为旧值。
*   **先更新 DB 再删缓存**：若删除缓存失败，后续读到旧缓存。

常用方案：
1.  **Cache Aside + 延迟双删**：更新 DB 前后各删除一次缓存，中间延迟一定时间。
2.  **订阅 binlog 异步更新**：通过 Canal 等工具监听数据库 binlog，异步更新或删除缓存，实现最终一致性。
3.  **分布式事务**：使用事务消息或两阶段提交保证 DB 和缓存操作原子性（成本高，不常用）。

---

#### 2. 延迟双删 (中)

*   **流程**：
    1.  先删除缓存。
    2.  更新数据库。
    3.  休眠一定时间（延迟）。
    4.  再次删除缓存。
*   **目的**：避免"先删缓存再更新 DB"过程中，其他线程将旧数据写回缓存导致的不一致。第二次删除用于清除这段时间内可能写入的旧缓存。
*   **缺点**：延迟时间难以精确设定，且仍存在短暂不一致窗口。

---

#### 3. 延迟删除缓存的时间到底设置要多久才合适呢？ (中)

*   **依据**：需覆盖"读请求回源并写回缓存"的完整耗时，一般设置为 **业务逻辑耗时 + 数据库查询耗时 + 网络耗时** 的总和，通常取值 **几百毫秒到 1~2 秒**。
*   **实际做法**：可通过压测统计读业务的平均和最差响应时间，延迟时间略高于"数据库查询 + 缓存写入"时间。也可结合异步监听 binlog 来确保缓存删除，不必强依赖固定延迟。

---

#### 4. 如何解决由操作失败导致的不一致性？重试！ (中)

当删除缓存或更新数据库操作失败时，可引入重试机制：
1.  **同步重试**：捕获失败后立即重试，适合短时偶发失败。
2.  **异步重试**：将失败操作写入消息队列（如 Kafka、RocketMQ），由消费者重试执行，重试多次后仍失败则转人工或告警。
3.  **订阅 binlog + 补偿**：监听数据库 binlog 变更，若缓存未成功失效则重复投递消息，直至缓存删除成功，实现最终一致性。

---

#### 5. 聊聊布隆过滤器原理 (低)

*   **定义**：一种空间效率很高的概率型数据结构，用于判断一个元素是否一定不存在或可能存在。
*   **结构**：由一个长二进制位数组和多个哈希函数构成。
*   **写入**：将元素通过 k 个哈希函数映射到位数组的 k 个位置，将这些位置的值置为 1。
*   **查询**：将查询元素同样哈希到 k 个位置，若所有位置的值都为 1，则认为元素**可能存在**；若任一位置为 0，则元素**一定不存在**。
*   **特性**：
    *   存在一定的误判率（会误判不存在为存在），但不会漏判（不会把存在的判断为不存在）。
    *   不支持删除操作（标准布隆过滤器），因为一个位置的 1 可能由多个元素共同设置。
*   **应用**：缓存穿透防护、URL 去重、黑名单过滤等。可调整位数组大小和哈希函数个数，在误判率和空间之间权衡。

---

## 四、分布式锁

---

### 4.1 基础实现

---

#### 1. 分布式锁概述 (高)

分布式锁是控制分布式系统中多个节点对共享资源互斥访问的一种机制，核心要求：
*   **互斥性**：任意时刻只有一个客户端持有锁。
*   **防死锁**：即使持有锁的客户端宕机，锁也能被释放（超时机制）。
*   **自己解锁**：加锁和解锁必须是同一客户端。
*   **高可用**：锁服务本身应具备高可用能力。

---

#### 2. 基本的分布式锁实现 (中)

使用 Redis `SET` 命令的扩展参数实现：
```
SET lock_key unique_value NX PX 30000
```
*   `NX`：仅键不存在时才设置，保证互斥。
*   `PX 30000`：设置 30 秒过期，防止死锁。
*   `unique_value`：客户端唯一标识（如 UUID+线程 ID），用于释放时验证。

**解锁流程（Lua 脚本保证原子性）**：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```
先比较 value 是否为自己设置的，匹配才删除，防止误删他人的锁。

---

#### 3. 释放错锁的问题 (中)

*   **问题场景**：线程 A 获取锁后执行超时，锁自动过期释放；线程 B 此时获取到锁；随后线程 A 恢复执行并释放锁，由于直接调用 `DEL`，导致线程 B 的锁被误删。
*   **根因**：删除锁时没有校验持有者身份。
*   **解决**：使用上述 Lua 脚本，对比 value 是否等于自己设置的唯一标识，匹配才删除，确保只释放自己持有的锁。

---

### 4.2 进阶机制

---

#### 1. 如何实现可重入锁 / Redisson 可重入锁原理 (中)

**可重入锁**：同一线程可多次获取同一把锁，需记录加锁次数，解锁次数与加锁次数相等时才真正释放。

**Redis 原生实现思路（Hash + Lua）**：
*   锁以 Hash 结构存储：`Key = lock_key`，`Field = 客户端唯一标识`，`Value = 重入次数`。
*   加锁 Lua 脚本：
    *   若锁不存在：`HSET lock_key client_id 1`，并设置过期时间。
    *   若锁存在且 field 等于当前客户端：`HINCRBY lock_key client_id 1`，重入计数 +1。
*   解锁 Lua 脚本：
    *   若 field 存在且值 > 1：`HINCRBY lock_key client_id -1`。
    *   若值 = 1：直接删除该 field，若 Hash 为空则删除整个锁 Key。

**Redisson 可重入锁原理**：
*   同样基于 Hash 数据结构，field 为连接管理器 ID+线程 ID 组成的唯一标识，value 为重入计数器。
*   加锁时若已存在相同线程标识则自增计数；解锁时递减，计数归零时删除锁并发送释放通知。
*   配合看门狗机制实现锁续约（见下文）。

---

#### 2. 如何实现锁的可重试 (中)

获取锁失败时，不立即返回失败，而是循环重试一定次数或时间：
*   **自旋 + 等待**：客户端在指定时间内循环尝试获取锁，每次失败后短暂休眠（如 10~50ms），直到获取成功或超时。
*   **发布/订阅通知**：获取失败后阻塞等待锁释放通知（Redisson 利用 Redis Pub/Sub 实现），收到通知后重新竞争，避免无效轮询。
*   Redisson 的 `tryLock(waitTime, leaseTime, unit)` 即内置了可重试、重入、续约等完整机制。

---

#### 3. 业务线程没执行完，锁超时释放了怎么办 / 如何实现超时续约 (中)

*   **问题**：锁的过期时间无法精确评估业务执行时间，若设置过短则锁提前释放，其他线程获取锁导致并发问题；设置过长则故障时恢复慢。
*   **解决方案：看门狗（Watchdog）自动续约**
    *   Redisson 默认开启看门狗：若未显式指定 `leaseTime`，加锁成功后自动启动一个定时任务，每 10 秒（默认 `lockWatchdogTimeout/3`）检查锁是否仍被当前线程持有，若是则将过期时间重置为 30 秒（`lockWatchdogTimeout`）。
    *   业务完成后显式解锁，看门狗随之取消。
    *   若应用进程崩溃，看门狗停止，锁到达过期时间后自动释放。
*   原生实现：获取锁后开启守护线程/定时器周期性延长锁的过期时间（需用 Lua 脚本校验持有者身份后 `PEXPIRE`）。

---

#### 4. 锁的主从一致性问题 (中)

*   **问题场景**：若使用 Redis 主从+哨兵架构，客户端 A 从主节点获取到锁，锁数据还未同步到从节点时主节点宕机，从节点被哨兵提升为新主，此时锁数据丢失，客户端 B 可从新主再次获取同一把锁，违反互斥性。
*   **理论解决（Redlock）**：见下文，向多个独立 Redis 节点顺序加锁，多数派成功才算获取。
*   **工程权衡**：多数场景下允许极低概率的锁失效，若对一致性要求极高，可考虑 ZooKeeper、etcd 等 CP 系统；或在 Redis 中引入 `WAIT` 命令强制同步副本（牺牲性能）。

---

#### 5. Redlock 红锁 (中)

Redlock 是 Redis 作者提出的分布式锁算法，旨在解决主从切换下的锁安全性问题。它假设有 N 个完全独立的 Redis 主节点（通常 N=5，不做主从），客户端执行以下步骤：

1.  获取当前时间戳。
2.  依次向所有 N 个节点请求加锁，使用相同的锁 Key 和唯一 value，超时时间远小于锁有效时间（如锁 10 秒，请求超时 5~50 毫秒）。
3.  若客户端在超过半数（N/2+1）的节点上成功加锁，且总耗时小于锁有效时间，则认为加锁成功。
4.  锁实际有效时间 = 锁原有效时间 - 加锁总耗时。
5.  若加锁失败，客户端需向所有节点发送解锁请求。

**争议**：
*   业界对其安全性有大量讨论，主要质疑：依赖系统时钟、节点延迟、GC 停顿等场景下仍可能失效。
*   实际生产中使用需谨慎评估，很多团队选用 ZooKeeper/etcd 实现强一致性锁，或直接使用 Redis 单实例（容忍极低概率失效）配合 Redisson 即可满足大部分场景。

---

## 五、高可用与集群

---

### 5.1 主从复制

---

#### 1. 如何保证 Redis 服务高可用？ (中)

*   **主从复制**：一主多从，数据冗余，读写分离，单点故障时可切换从节点提升为主。
*   **哨兵机制**：自动监控主从节点状态，主节点故障时自动执行故障转移，选举新主节点。
*   **集群模式**：多主多从，数据分片存储，单分片内具备主从高可用，支持水平扩展。
*   **持久化与备份**：开启 RDB + AOF 混合持久化，定期异地备份数据。
*   **资源隔离与监控**：独立部署、资源充足，配合监控告警及时处理故障。

---

#### 2. 什么是主从复制 (中)

将一台 Redis 主节点的数据复制到一台或多台从节点，数据流向为单向（主→从）。
*   **作用**：数据冗余备份、读写分离提升读吞吐量、为故障转移提供基础。
*   **过程**：从节点执行 `REPLICAOF` 后，与主建立连接，先进行全量同步，后续增量同步。

---

#### 3. 讲一下 Redis 主从同步中的完全同步 (低)

完全同步发生在从节点首次连接或复制偏移量差距过大时，过程如下：
1.  从节点发送 `PSYNC ? -1` 请求全量同步。
2.  主节点执行 `BGSAVE` 生成 RDB 快照，同时将生成期间的新写命令写入 replication buffer。
3.  主节点将 RDB 文件发送给从节点，从节点清空自身数据库并加载 RDB。
4.  主节点将 replication buffer 中的增量命令发送给从节点，从节点重放至一致状态。

---

#### 4. 讲一下 Redis 主从同步中的增量同步 (低)

当主从因网络闪断等原因短暂断开，且主节点的复制积压缓冲区（repl_backlog_buffer）中还保留着断开期间的命令时，走增量同步。
*   从节点重连后发送 `PSYNC <replid> <offset>`，告知自己已同步的偏移量。
*   主节点检查 repl_backlog_buffer 中是否包含该 offset 之后的命令，若有，则将该部分命令发送给从节点，从节点重放即可追上。

---

#### 5. 主服务器怎么知道要将哪些增量数据发送给从服务器呢？ (中)

通过 **复制偏移量** 和 **复制积压缓冲区（repl_backlog_buffer）**：
*   主节点维护一个全局复制偏移量，每执行一条写命令，偏移量增加命令字节数。
*   从节点定期向主节点报告自己当前已处理的偏移量。
*   主节点对比二者，若差值在 repl_backlog_buffer 范围内，则从缓冲区中取出对应偏移量之后的命令发给从节点；否则需要全量同步。

**那 repl_backlog_buffer 缓冲区是什么时候写入的呢？**
主节点在执行写命令时，**同时**：
*   执行该命令修改自身数据；
*   将命令传播给所有已连接的从节点；
*   将命令写入 repl_backlog_buffer（固定大小的环形缓冲区），并更新全局复制偏移量。

该缓冲区从主节点启动并首次有从节点连接时开始写入，持续记录最近的写命令。

---

### 5.2 哨兵机制

---

#### 1. 主从复制与 Sentinel 哨兵机制 (中)

*   **主从复制**：解决数据冗余和读写分离，但不能自动故障转移。主节点宕机需人工介入将从节点提升为主。
*   **哨兵机制**：运行在独立进程中的监控程序，监控主从运行状态，主节点故障时自动选主并通知客户端切换，弥补主从复制无法自动容灾的缺陷。通常部署多个哨兵（≥3 个）形成哨兵集群，防止单点误判。

---

#### 2. Sentinel（哨兵）有什么作用？ (中)

1.  **监控**：周期性 `PING` 检查主从节点和其余哨兵是否存活。
2.  **通知**：当节点状态变化时，通过 API 或 Pub/Sub 通知运维或客户端。
3.  **自动故障转移**：主节点客观下线后，从从节点中选举新主，将其他从节点重定向到新主，并将旧主降为从节点。
4.  **配置提供者**：客户端可向哨兵询问当前主节点地址，实现动态切换。

---

#### 3. 聊聊哨兵机制的选主算法 (低)

1.  **过滤**：排除不健康的从节点（主观下线、断线、5 秒内无 `PING` 回复、与主断开超时）。
2.  **优先级排序**：选择 `replica-priority` 最小的从节点（该值在配置文件中设置，越小优先级越高）。
3.  **偏移量比较**：优先级相同则选择复制偏移量最大的从节点（数据最新）。
4.  **运行 ID**：若偏移量也相同，选择运行 ID 字典序最小的从节点。

---

#### 4. 简单讲一下 Raft 算法 (低)

Raft 是一种分布式共识算法，用于管理多节点状态的一致复制，核心机制：
*   **Leader 选举**：节点有三种角色（Leader、Follower、Candidate）。Leader 定期发送心跳，Follower 心跳超时则转为 Candidate 发起投票，获多数票成为新 Leader。
*   **日志复制**：客户端请求由 Leader 处理，Leader 将日志条目追加到本地日志，并发给 Followers，收到多数确认后提交，通知 Followers 提交，状态机应用日志。
*   **安全性**：保证已提交的日志不会被覆盖，选举限制只有包含最新日志的节点才能成为 Leader。
Redis Sentinel 的选举借鉴了 Raft 思想，但并非完整的 Raft 实现。

### 5.3 Cluster 集群

---

#### 1. Redis 缓存的数据量太大怎么办？ (中)

1.  **Redis Cluster**：将数据分散到多个分片，每个节点存储部分数据，突破单机内存限制。
2.  **冷热数据分离**：热数据存 Redis，冷数据存数据库或其他廉价存储，通过淘汰策略或定时任务迁移。
3.  **优化数据结构**：使用更节省内存的编码（如 ziplist 替代普通 List/Hash），合理设置 `hash-max-ziplist-entries` 等参数。
4.  **过期策略 + 内存淘汰**：设置合理 TTL，及时清理无用数据，配置 allkeys-lru/LFU 淘汰低频数据。
5.  **垂直扩展**：升级单机内存（有上限，且 fork 开销增大）。

---

#### 2. Redis Cluster 的作用？ (中)

*   **数据分片**：将数据自动切分到多个节点，突破单机内存和吞吐量限制，支持水平扩容。
*   **高可用**：每个分片支持主从复制，主节点故障时集群自动将从节点提升为主。
*   **去中心化**：节点间通过 Gossip 协议交换状态，客户端可连接任意节点，请求自动重定向到正确分片。
*   **弹性扩展**：在线增加/删除节点，数据槽自动迁移。

---

#### 3. Redis Cluster 是如何分片的？ (中)

*   **哈希槽分片**：Redis Cluster 将整个键空间划分为 **16384 个哈希槽**，每个主节点负责一部分槽。
*   **槽计算**：对 key 有效部分执行 `CRC16(key) % 16384` 得到槽号。
    *   如 `user:{id}` 可利用 `{}` 哈希标签，让相关 key 落于同一槽。
*   **定位节点**：客户端启动时可获取槽到节点的映射表并缓存，直接向目标节点发送命令。若槽归属已变，节点返回 `MOVED` 错误（重定向）或 `ASK` 错误（迁移中临时转向），客户端更新本地映射后重试。
