## 网络基础

### OSI 和 TCP/IP 网络分层模型

**OSI 七层模型**（理论标准）

| 层级 | 名称       | 主要功能                                  |
| ---- | ---------- | ----------------------------------------- |
| 7    | 应用层     | 为用户应用程序提供网络服务接口            |
| 6    | 表示层     | 数据格式转换、加密、压缩                  |
| 5    | 会话层     | 建立、管理和终止会话连接                  |
| 4    | 传输层     | 端到端可靠/不可靠传输、差错控制、流量控制 |
| 3    | 网络层     | 逻辑寻址、路由选择、拥塞控制              |
| 2    | 数据链路层 | 物理寻址、成帧、差错检测                  |
| 1    | 物理层     | 比特流传输，定义物理介质、电压、速率等    |

**TCP/IP 四层模型**（事实标准）

| 层级 | 名称       | 对应 OSI 层            | 常见协议             |
| ---- | ---------- | ---------------------- | -------------------- |
| 4    | 应用层     | 应用层、表示层、会话层 | HTTP, FTP, DNS, SMTP |
| 3    | 传输层     | 传输层                 | TCP, UDP             |
| 2    | 网络层     | 网络层                 | IP, ICMP, ARP        |
| 1    | 网络接口层 | 数据链路层、物理层     | Ethernet, Wi-Fi      |

实际教学中，常采用**五层模型**，将网络接口层拆分为数据链路层和物理层，综合了两者优点。

---

### 应用层有哪些常见的协议

- **HTTP / HTTPS**：超文本传输协议，用于 Web 访问（HTTPS 加入 TLS/SSL 加密）。
- **FTP**：文件传输协议，用于文件上传和下载。
- **SMTP**：简单邮件传输协议，用于发送邮件。
- **POP3 / IMAP**：邮件接收协议，POP3 下载后删除服务器副本，IMAP 保留服务器副本。
- **DNS**：域名系统，将域名解析为 IP 地址。
- **Telnet / SSH**：远程登录协议，SSH 提供加密。
- **SNMP**：简单网络管理协议，监控和管理网络设备。
- **DHCP**：动态主机配置协议，自动分配 IP 地址。
- **NTP**：网络时间协议，同步时钟。

---

### 传输层常见协议

**TCP（传输控制协议）**
- **面向连接**：传输前需三次握手建立连接，结束后四次挥手。
- **可靠传输**：通过序号、确认应答、重传机制保证数据无差错、不丢失、不重复、按序到达。
- **流量控制**：滑动窗口机制，防止发送过快压垮接收方。
- **拥塞控制**：慢开始、拥塞避免、快重传、快恢复算法。
- **面向字节流**：将应用层数据看作连续字节流。
- **适用场景**：对可靠性要求高的应用，如 Web 浏览、邮件、文件传输。

**UDP（用户数据报协议）**
- **无连接**：直接发送数据，不建立连接。
- **不可靠**：不保证送达，不保证顺序，无确认机制。
- **面向报文**：保留应用层报文边界，一次发送一个完整报文。
- **轻量高效**：首部仅 8 字节，没有连接管理开销，速度快。
- **适用场景**：实时性要求高、允许部分丢包的应用，如音视频直播、在线游戏、DNS 查询。

---

### 为何要分层

- **降低复杂性**：将庞大复杂的网络通信问题分割为若干小功能层，各层专注自身职责，设计和实现更简单。
- **模块化与解耦**：层间通过定义好的接口交互，内部实现可独立变化，不影响其他层（如应用程序不关心底层是光纤还是无线）。
- **标准化与互操作性**：各层协议标准化后，不同厂商的设备和软件能相互通信（如不同操作系统实现 TCP/IP 即可互通）。
- **易于开发和维护**：可以单独更新某一层的技术而不影响整个系统（如 HTTP 从 1.1 升级到 2 无需修改 TCP）。
- **便于教学和排错**：分层结构清晰，可按层分析网络问题，定位故障。

### TCP 和 UDP 的特点、不同之处

| 对比项       | TCP                                        | UDP                                           |
| ------------ | ------------------------------------------ | --------------------------------------------- |
| **连接性**   | 面向连接，需建立连接（三次握手）           | 无连接，直接发送                              |
| **可靠性**   | 可靠传输，保证数据不丢、不重、有序         | 不可靠，不保证送达和顺序                      |
| **传输方式** | 面向字节流，无边界                         | 面向报文，保留边界                            |
| **头部开销** | 20 字节首部                                | 8 字节首部                                    |
| **速度**     | 较慢，有拥塞控制、流量控制                 | 较快，无这些机制                              |
| **适用场景** | 文件传输、网页浏览、邮件等需要可靠性的场景 | 音视频直播、DNS、在线游戏等实时性要求高的场景 |

**TCP 特点**：可靠、有序、有连接、流式传输，代价是开销大、延迟较高。  
**UDP 特点**：不可靠、无序、无连接、报文传输，优点是轻量、速度快、实时性好。

### 三次握手

**过程**（客户端主动打开，服务器被动打开）：

1. **第一次握手**  
   客户端发送 SYN 报文（SYN=1，seq=x，随机初始序列号），客户端进入 **SYN_SENT** 状态。

2. **第二次握手**  
   服务器收到 SYN，回复 SYN+ACK 报文（SYN=1，ACK=1，seq=y，ack=x+1），服务器进入 **SYN_RCVD** 状态。

3. **第三次握手**  
   客户端收到 SYN+ACK，回复 ACK 报文（ACK=1，seq=x+1，ack=y+1），客户端进入 **ESTABLISHED** 状态。服务器收到后也进入 **ESTABLISHED** 状态，连接建立成功。

---

### 为什么一定要三次握手，两次不行吗？

**不能，两次握手无法防止失效的连接请求到达服务器，导致资源浪费。**

具体原因：
- 如果只有两次握手，客户端发送 SYN 后，服务器收到后直接进入 ESTABLISHED 状态，并回复 SYN+ACK。但网络可能延迟，客户端迟迟收不到确认，会重发 SYN。之前的 SYN 可能因网络阻塞延迟到达服务器，服务器会认为这是一个新连接请求，直接建立连接并分配资源。客户端此时早已放弃该连接，服务器却白白维护着一个无效连接，造成资源浪费。
- 三次握手则不同：服务器收到 SYN 后进入 SYN_RCVD 状态，需等待客户端第三次 ACK 才建立连接。如果该 SYN 是旧的，客户端不会响应，服务器超时后回收资源，避免了无效连接。

此外，三次握手也是双方确认自己和对方的收发能力都正常的必要过程：第一次证明客户端的发送正常；第二次证明服务器的接收和发送正常；第三次证明客户端的接收正常。

### 四次挥手

**过程**（假设客户端主动关闭）：

1. **第一次挥手**  
   客户端发送 FIN 报文（FIN=1，seq=u），进入 **FIN_WAIT_1** 状态，表示无数据要发送。

2. **第二次挥手**  
   服务器收到 FIN，回复 ACK 报文（ACK=1，seq=v，ack=u+1），进入 **CLOSE_WAIT** 状态。客户端收到后进入 **FIN_WAIT_2** 状态。此时客户端到服务器的方向已关闭，但服务器仍可发送数据。

3. **第三次挥手**  
   服务器发送完剩余数据后，发送 FIN 报文（FIN=1，ACK=1，seq=w，ack=u+1），进入 **LAST_ACK** 状态。

4. **第四次挥手**  
   客户端收到 FIN，回复 ACK 报文（ACK=1，seq=u+1，ack=w+1），进入 **TIME_WAIT** 状态，等待 2MSL 后进入 CLOSED。服务器收到 ACK 后立即进入 CLOSED。

**为什么需要四次？**  
TCP 是全双工通信，关闭连接需要双方各自确认关闭。收到对方的 FIN 只表示对方不再发送数据，己方仍可发送剩余数据，因此 ACK 和 FIN 通常分开发送，导致至少四次挥手。

### HTTP 为什么不安全？

HTTP 在传输过程中是**明文**的，数据未经过任何加密处理，存在以下安全风险：

1. **窃听风险**  
   攻击者可通过网络嗅探工具直接获取传输的敏感信息（如账号密码、银行卡号）。

2. **篡改风险**  
   数据在传输过程中可被中间人拦截并篡改，接收方收到的可能是被植入恶意代码的内容。

3. **冒充风险**  
   攻击者可伪装成目标服务器，实施中间人攻击（如钓鱼网站），用户无法验证通信方的真实身份。

### HTTP 和 HTTPS 区别

| 对比项       | HTTP                        | HTTPS                              |
| ------------ | --------------------------- | ---------------------------------- |
| **安全性**   | 明文传输，不安全            | 密文传输，安全                     |
| **加密**     | 无加密                      | 基于 SSL/TLS 协议加密              |
| **端口**     | 默认 80                     | 默认 443                           |
| **证书**     | 不需要                      | 需要 CA 颁发数字证书验证服务器身份 |
| **连接建立** | 简单 TCP 三次握手后即可通信 | 需 TCP 三次握手 + SSL/TLS 握手     |
| **SEO**      | 搜索引擎可能降权            | 搜索引擎优先收录                   |
| **速度**     | 较快（无加解密开销）        | 较慢（额外握手和加解密消耗）       |

---

### SSL/TLS 怎么确保安全通信，HTTPS 怎么保证安全？

HTTPS = HTTP + SSL/TLS，通过 TLS 协议提供以下三方面的安全保障：

**1. 加密（防窃听）**  
使用**对称加密**对传输数据进行加密，双方共享会话密钥，第三方无法解密。会话密钥通过**非对称加密**（如 RSA、ECDHE）安全交换，确保只有通信双方知晓。

**2. 完整性校验（防篡改）**  
使用 MAC（消息认证码）或 HMAC 对消息进行摘要和校验，接收方可验证数据在传输过程中是否被篡改。

**3. 身份认证（防冒充）**  
服务器持有由 CA（证书颁发机构）签发的**数字证书**，证书包含服务器公钥和身份信息。客户端验证证书合法性后，使用公钥与服务器建立安全通信，确保连接的是真实服务器而非假冒者。

### HTTPS 是如何建立连接的

HTTPS 连接 = TCP 三次握手 + TLS/SSL 握手，以常见的 ECDHE + RSA 为例：

**1. 客户端发出 Client Hello**  
- 发送支持的 TLS 版本、加密套件列表（如 TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256）
- 发送一个随机数（Random_C）

**2. 服务器回应 Server Hello**  
- 确认使用的 TLS 版本和加密套件
- 发送随机数（Random_S）
- 发送包含公钥的数字证书

**3. 客户端验证证书**  
- 用内置的 CA 公钥验证证书合法性（有效期、域名匹配、颁发者可信）
- 提取服务器公钥

**4. 密钥交换（ECDHE 算法）**  
- 服务器发送 Server Key Exchange：包含 ECDHE 临时公钥，并用私钥签名
- 客户端验证签名后，发送 Client Key Exchange：包含客户端 ECDHE 临时公钥
- 双方根据各自的私钥和对方公钥计算得到相同的 Pre-Master Secret
- 结合 Random_C + Random_S + Pre-Master Secret 通过 PRF 推导出**会话密钥**（对称加密用）

**5. 完成握手**  
- 客户端发送 Change Cipher Spec，告知之后用会话密钥加密
- 客户端发送 Finished（加密的握手校验信息）
- 服务器回应 Change Cipher Spec + Finished
- 握手结束，开始用会话密钥对称加密传输 HTTP 数据

整个过程通过非对称加密保护密钥交换，之后用对称加密高效传输数据。
