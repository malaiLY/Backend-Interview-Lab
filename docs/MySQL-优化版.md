## 一、基础架构与设计规范

---

### 1. 数据库三大范式 (中)

**一句话概括：** 范式是关系型数据库设计的规范，目的是为了**减少数据冗余、消除异常（插入/更新/删除异常），保证数据的完整性**。

*   **第一范式 (1NF)：属性不可再分（原子性）。**
    *   **解释：** 表中的每一列都必须是不可拆分的最小数据单元。
    *   **反例：** 某表有一个字段叫"联系方式"，里面同时存了"手机号-微信号"。这就违反了 1NF，必须拆分成"手机号"和"微信号"两个独立字段。
*   **第二范式 (2NF)：消除部分依赖（要求表必须有主键，且非主键字段必须完全依赖主键）。**
    *   **解释：** 这一条主要针对**联合主键**。如果表的主键由两个列组成（比如学号+课程号），那么其他字段（比如学生姓名）不能只依赖其中某一个列（只依赖学号），必须依赖整个主键。
    *   **解法：** 把"学生信息"和"课程信息"拆分成不同的表。
*   **第三范式 (3NF)：消除传递依赖（非主键字段必须直接依赖主键，不能间接依赖）。**
    *   **解释：** 表中的字段之间不能互相依赖。
    *   **反例：** 员工表中有：`员工ID(主键)`、`部门ID`、`部门名称`。这里"部门名称"依赖于"部门ID"，而"部门ID"依赖于主键。这就形成了传递依赖，导致如果部门改名了，要更新所有该部门员工的记录。
    *   **解法：** 把"部门名称"抽离出去，建立一张独立的"部门表"。

*(💡 面试高级加分项：)*
**实际开发中的反范式设计：** 面试时一定要补充一句："虽然三大范式很好，但在实际高并发业务开发中，我们经常会**故意打破范式（反范式设计）**。为了提高查询性能、减少多表 Join，我们会故意在单表里增加一些冗余字段（比如在订单表里直接存入商品名称），用**空间换时间**。"

### 2. CHAR 和 VARCHAR 有什么区别？ (中)

主要从存储方式、性能和使用场景三个维度来回答：

*   **长度与存储：**
    *   **CHAR：** **定长**字符串。如果你定义了 `CHAR(10)`，哪怕你只存入 "abc"（3 个字符），MySQL 也会在末尾用空格补全剩下的 7 个位置，永远占用固定空间。
    *   **VARCHAR：** **变长**字符串。如果你定义了 `VARCHAR(10)`，存入 "abc"，它只会占用实际的 3 个字符空间，外加 **1 到 2 个字节** 用来专门记录该字符串的实际长度。
*   **性能效率：**
    *   **CHAR** 的存取效率**高于** VARCHAR。因为长度固定，数据库引擎在分配内存、查找定位时更快，不会产生内存碎片。
    *   **VARCHAR** 每次修改数据如果长度变了，可能需要重新分配存储空间，效率稍低。
*   **实际使用场景：**
    *   **用 CHAR 的场景：** 存储长度绝对固定、或者长度极短的数据。例如：**UUID**、**MD5 加密后的密码**、身份证号、手机号、性别（男/女）。
    *   **用 VARCHAR 的场景：** 绝大多数场景，长度不固定的文本。例如：用户名、文章标题、家庭住址、备注信息等。

### 3. SQL 语句的执行顺序 (中)

**核心要点：** 你在代码里写的 SQL 语句的顺序（`SELECT ... FROM ... WHERE ...`），**并不是** MySQL 底层实际执行的顺序。

一个完整的查询 SQL，底层的**真正执行顺序**如下：

1.  **`FROM` / `JOIN`：** 确定数据源，首先去磁盘拿哪几张表，如果是 JOIN 会生成一个笛卡尔积的临时表。
2.  **`ON`：** 按照联表条件，过滤刚才生成的临时表数据。
3.  **`WHERE`：** 对表数据进行行级别的条件过滤。
4.  **`GROUP BY`：** 将过滤后的数据进行分组。
5.  **`HAVING`：** 对分组之后的数据（或者聚合函数如 SUM/COUNT 的结果）进行再次过滤。
6.  **`SELECT`：** 提取要查询的具体列，这一步才开始计算 `SELECT` 后面的别名和表达式。
7.  **`DISTINCT`：** 剔除重复的行。
8.  **`ORDER BY`：** 对最终产生的结果集进行排序。
9.  **`LIMIT`：** 截取需要的条数（分页），返回给客户端。

*(💡 面试经典避坑指南：)*
面试官经常会问："**为什么不能在 WHERE 语句中使用 SELECT 定义的别名？**"
你就可以用这个顺序回答："因为从执行顺序来看，**`WHERE` 的执行优先级在 `SELECT` 之前**。当底层执行到 `WHERE` 过滤时，`SELECT` 还没开始执行，所以底层根本不知道这个别名是什么，会报错找不到列。"

### 4. SQL 语句的执行过程 / MySQL 架构是什么 (中)

**回答策略：** 先总体介绍 MySQL 的分层架构，然后再串起一条 SQL 语句的具体执行流程。

**MySQL 的架构总体分为三层：**
1.  **连接层 (Connection Layer)：** 负责处理客户端的连接请求、进行鉴权认证（账号密码）、并维护连接池。
2.  **服务层 (Server Layer)：** MySQL 的核心大脑，涵盖了大多数核心服务功能。所有的跨存储引擎功能（如内置函数、视图、触发器等）都在这一层实现。
3.  **引擎层 (Storage Engine Layer)：** 真正的底层数据管家，采用**可插拔式**设计。负责 MySQL 中数据的真正存储和提取。

**一条 SELECT 语句的完整执行过程：**
1.  **建立连接：** 客户端通过 TCP 与 MySQL 服务器建立连接并进行身份验证。
2.  **查询缓存 (Query Cache)：** （*注意：MySQL 8.0 已经彻底废除此功能*）。如果开启了缓存，MySQL 会用 SQL 语句作为 Key 去缓存查，命中则直接返回。
3.  **解析器 (Parser)：** 如果没命中缓存，MySQL 会对 SQL 语句进行**词法分析和语法分析**，生成一棵"抽象语法树（AST）"。如果有语法错误，就在这里报错。
4.  **优化器 (Optimizer)：** MySQL 并不一定会完全按照你写的 SQL 去执行。优化器会评估多种执行方案（比如决定使用哪个索引、多表 Join 的连接顺序），并选择它认为**成本最低（最优）**的"执行计划"。
5.  **执行器 (Executor)：** 开始真正的执行。执行器会先校验用户对该表的权限，然后**根据执行计划，调用底层存储引擎提供的 API** 获取数据，最终将结果集返回给客户端。

---

### 5. 数据库存储引擎有哪些 (高)

MySQL 采用的是**可插拔的存储引擎架构**，可以针对不同的表使用不同的存储引擎。最常用的有以下几种：

1.  **InnoDB：** MySQL 5.5 以后的**默认存储引擎**。它是为处理巨大数据量时的最大性能设计。支持事务、支持行级锁、支持外键，数据安全性极高，是**日常业务开发 99% 的选择**。
2.  **MyISAM：** MySQL 5.5 之前的默认引擎。不支持事务和外键，只支持表锁。它的特点是读取速度极快，适合以读为主、对数据完整性要求不高的场景。
3.  **Memory：** 将所有数据保存在**内存（RAM）**中，访问速度极快。但一旦数据库重启或断电，数据就会全部丢失。通常用于临时表或者缓存字典表。
4.  **Archive：** 拥有极高的压缩比，只支持 `INSERT` 和 `SELECT` 操作，不支持索引。极其适合用来存储大量的历史归档数据或系统操作日志。

---

### 6. InnoDB 和 MyISAM 的区别 (高)

这是 MySQL 面试中**绝对的超高频题**，建议从以下 6 个维度进行对比作答：

1.  **事务支持（核心区别）：**
    *   **InnoDB** 支持完整的 ACID 事务，支持事务的提交（Commit）和回滚（Rollback）。
    *   **MyISAM** **不**支持事务。
2.  **锁的粒度（并发性能）：**
    *   **InnoDB** 默认支持**行级锁**（Row-level Lock），也支持表锁。在并发写入时，只锁住当前操作的行，大大提高了高并发下的处理能力。
    *   **MyISAM** 只支持**表级锁**（Table-level Lock）。哪怕只更新一行数据，也会锁住整张表，并发写性能极差。
3.  **索引结构（数据物理存储方式）：**
    *   **InnoDB** 使用的是**聚簇索引（Clustered Index）**。它的主键索引的叶子节点中直接包含了完整的行数据（数据和索引绑在一起）。
    *   **MyISAM** 使用的是**非聚簇索引（Non-clustered Index）**。它的索引和数据文件是分离的，叶子节点里存的只是指向物理数据内存地址的指针。
4.  **外键支持：**
    *   **InnoDB** 支持外键约束（Foreign Key），能保证数据的完整性和关联性。
    *   **MyISAM** **不**支持外键。
5.  **崩溃恢复机制：**
    *   **InnoDB** 拥有安全的崩溃恢复能力。它依靠 `redo log`（重做日志），即使数据库意外宕机，重启后也能恢复未写进磁盘的数据。
    *   **MyISAM** 没有这种机制，宕机极容易导致数据损坏或丢失。
6.  **`COUNT(*)` 的性能：**
    *   **MyISAM** 内部维护了一个变量，专门记录表的总行数。执行 `SELECT COUNT(*)` 时直接返回，速度极快（$O(1)$）。
    *   **InnoDB** 因为有 MVCC（多版本并发控制）机制，不同事务在同一时刻看到的行数可能不同，所以没有专门记录总行数。执行 `COUNT(*)` 时需要全表（或全索引）扫描，速度较慢（$O(N)$）。

*(💡 面试总结加分项：)*
"综合来看，**MyISAM** 已经被时代边缘化了，现在除非是纯只读的历史报表系统，其他所有业务场景（尤其涉及支付、订单、高并发写）都应该**无条件选择 InnoDB**。"

## 二、事务与并发控制

---

### 2.1 事务基础

---

#### 1. 什么是数据库事务？ (中)

**数据库事务（Transaction）** 是指作为单个逻辑工作单元执行的一系列数据库操作（SQL 语句）。
这些操作**要么全部成功执行，要么全部失败回滚**，是一个不可分割的工作实体。

*   **经典例子**：银行转账。A 向 B 转账 100 元，包含两个操作：A 账户扣减 100 元，B 账户增加 100 元。这两个操作必须被放在同一个事务中，不能出现 A 扣钱了但 B 没收到的情况。

---

#### 2. 事务四大特性（ACID） (高)

事务必须具备四个核心特性，简称 **ACID**：

*   **A - 原子性（Atomicity）**：
    事务是最小的执行单位，不允许分割。事务的原子性确保动作**要么全部完成，要么完全不起作用**。
    *(底层实现：MySQL 通过 `undo log` 回滚日志实现，失败时利用它撤销已执行的操作)*
*   **C - 一致性（Consistency）**：
    执行事务前后，数据保持一致的状态。比如转账前后，A 和 B 的账户总金额必须保持不变。一致性是事务的最终目的。
*   **I - 隔离性（Isolation）**：
    并发访问数据库时，一个用户的事务不被其他事务所干扰，各并发事务之间数据库是独立的。
    *(底层实现：MySQL 通过 `锁机制` 和 `MVCC` 实现)*
*   **D - 持久性（Durability）**：
    一个事务被提交之后，它对数据库中数据的改变是持久的，即使数据库发生故障也不应该对其有任何影响。
    *(底层实现：MySQL 通过 `redo log` 重做日志实现)*

---

#### 3. 隔离性产生的问题 (高)

如果不考虑隔离性，多个事务并发执行时，会导致以下三大问题（严重程度依次递增）：

1.  **脏读（Dirty Read）**：
    *   **现象**：事务 A 读取了事务 B **尚未提交**的数据。如果 B 回滚了，A 读到的就是无效的"脏数据"。
2.  **不可重复读（Non-repeatable Read）**：
    *   **现象**：在一个事务内，多次读取**同一条数据**，结果不一样。
    *   **原因**：在两次读取之间，另一个并发事务**修改（UPDATE/DELETE）**了该数据并提交。
3.  **幻读（Phantom Read）**：
    *   **现象**：在一个事务内，按照同一个条件多次查询，后一次查询读到了前一次查询没有看到的**新行**（像产生幻觉一样）。
    *   **原因**：在两次查询之间，另一个并发事务**插入（INSERT）**了新数据并提交。

*(注：不可重复读侧重于**数据内容的修改**，幻读侧重于**数据条数的增减**)*

---

#### 4. 事务的隔离级别 (高)

为了解决上述并发问题，SQL 标准定义了四种隔离级别（隔离级别越高，并发性能越差）：

1.  **读未提交（Read Uncommitted）**：
    *   最低级别，允许读取尚未提交的数据。
    *   **解决**：什么也没解决。存在脏读、不可重复读、幻读。
2.  **读已提交（Read Committed / RC）**：
    *   允许事务读取已经提交的数据。（**Oracle 默认隔离级别**）
    *   **解决**：解决了脏读。仍存在不可重复读、幻读。
3.  **可重复读（Repeatable Read / RR）**：
    *   保证在同一个事务中多次读取同样记录的结果是一致的。（**MySQL InnoDB 默认隔离级别**）
    *   **解决**：解决了脏读、不可重复读。*（注意：MySQL InnoDB 在 RR 级别下，通过 Next-Key Lock 顺带也解决了很大一部分幻读问题）*。
4.  **串行化（Serializable）**：
    *   最高的隔离级别，完全服从 ACID，所有的事务依次逐个执行，事务之间互不干扰。
    *   **解决**：解决了所有并发问题。但性能极低。

---

#### 5. MySQL 的隔离级别是怎么实现的？ (高)

MySQL InnoDB 引擎主要通过 **MVCC（多版本并发控制）** 和 **锁机制** 来实现隔离级别：

*   **Read Uncommitted**：直接读取最新的数据行，不加锁，也不用 MVCC。
*   **Serializable**：对读写操作全面加锁（读加共享锁，写加排他锁），退化为串行执行，不用 MVCC。
*   **RC（读已提交）实现：基于 MVCC**
    *   每次执行查询（Select）语句时，都会**重新生成一个新的 Read View（读视图）**。
    *   这保证了每次查询都能看到其他事务刚刚提交的最新数据，所以会出现"不可重复读"。
*   **RR（可重复读）实现：基于 MVCC + 锁**
    *   **快照读（普通的 select）**：利用 **MVCC**。在事务**第一次**执行查询时生成一个 Read View，此后该事务内的所有普通查询都使用这同一个 Read View。因此别人怎么修改提交，都不会影响当前事务的查询结果，解决了不可重复读。
    *   **当前读（update/delete/select ... for update）**：利用 **Next-Key Lock（临键锁 = 记录锁 + 间隙锁 Gap Lock）**。不仅锁住查出来的记录，还会锁住记录之间的间隙，防止其他事务在这个间隙插入新数据，从而**解决了幻读问题**。

---

#### 6. 单条 update 语句是原子性的吗？ (中)

**答案是：是的，绝对是原子性的。**

**原理解析：**
1.  **单条 SQL 本身就是一个隐式事务**：在 MySQL 等关系型数据库中，默认开启了 `autocommit`（自动提交）。这意味着你执行单条 `UPDATE`、`INSERT` 或 `DELETE` 语句时，数据库会自动为它开启一个事务，并在语句执行完成后自动提交。
2.  **执行失败会整体回滚**：假设一条 `UPDATE` 语句要更新 1000 行记录，在更新到第 500 行时，发生了死锁、断电或违反了唯一性约束报错。那么数据库会利用 `undo log` 将前面已经更新的 499 行数据**全部回滚**到修改前的状态。
3.  **结论**：这条 `UPDATE` 语句要么 1000 行全更新成功，要么一行都不更新，完全符合原子性（Atomicity）的要求。

---

### 2.2 MVCC（多版本并发控制）

---

#### 1. 什么是 MVCC？ (中)

**MVCC (Multi-Version Concurrency Control，多版本并发控制)** 是一种用于实现数据库并发访问控制的技术。

简单来说，**它就像是给数据库的数据做"版本控制"（类似 Git）**。当一个事务要修改某行数据时，MVCC 不会直接覆盖原来的数据，而是生成一个该行数据的新版本。同时，允许其他事务读取旧版本的数据。

**核心思想**："读不加锁，读写不冲突"。

---

#### 2. MVCC 可以为数据库解决什么问题？ (中)

MVCC 主要解决了以下两大核心问题：

1.  **极大地提升了并发性能**：
    在传统的锁机制下，"读写"是互斥的（读会阻塞写，写会阻塞读）。MVCC 实现了**普通的查询（快照读）不需要加锁**，使得"读写不冲突"，大幅提升了数据库的并发处理能力。
2.  **解决了并发带来的安全问题（隔离级别）**：
    MVCC 结合不同的配置，可以在不加锁的情况下，解决**脏读**、**不可重复读**，并在一定程度上配合解决**幻读**问题，实现了 RC（读已提交）和 RR（可重复读）隔离级别。

---

#### 3. MVCC 的实现原理？ (高)

MySQL InnoDB 的 MVCC 底层是由 **"三个火枪手"** 共同实现的：**隐藏字段 + Undo Log（回滚日志）+ ReadView（读视图）**。

1.  **隐藏字段**：
    InnoDB 会在每一行记录的末尾偷偷加上几个隐藏字段，最核心的是：
    *   `trx_id`：记录最近一次**修改（或插入）**这行数据的事务 ID。
    *   `roll_pointer`：回滚指针，指向这行数据的上一个版本。
2.  **Undo Log（版本链）**：
    当一个事务修改数据时，旧版本的数据会被存入 Undo Log 中。通过每行记录的 `roll_pointer` 指针，当前最新数据和 Undo Log 里的旧数据被串联起来，形成一条**历史版本链**。
3.  **ReadView（读视图）**：
    用来判断当前事务在执行查询时，到底应该看版本链上的哪个版本的数据（可见性判断）。*（详见下一题）*

---

#### 4. ReadView 是什么？ (高)

**ReadView（读视图）** 是一个事务在执行**快照读**（普通 Select）时，由系统生成的一个"快照"。它就像一个摄像机，记录了当前时刻数据库中**所有活跃（未提交）的事务状态**。

**ReadView 包含四个核心字段：**
*   `creator_trx_id`：创建当前 ReadView 的事务 ID（我自己的事务 ID）。
*   `m_ids`：生成 ReadView 时，当前系统中**所有活跃（未提交）**的事务 ID 列表。
*   `min_trx_id`：活跃事务列表中最小的事务 ID。
*   `max_trx_id`：生成 ReadView 时系统应该分配给**下一个**事务的 ID（也就是最大活跃事务 ID + 1）。

**可见性判断规则（沿着版本链对比数据的 `trx_id`）：**
1.  如果 `trx_id == creator_trx_id`：这行数据是我自己修改的，**可见**。
2.  如果 `trx_id < min_trx_id`：修改这行数据的事务在 ReadView 生成前早就提交了，**可见**。
3.  如果 `trx_id >= max_trx_id`：修改这行数据的事务是在 ReadView 生成之后才开启的，**不可见**。
4.  如果 `min_trx_id <= trx_id < max_trx_id`：判断 `trx_id` 是否在活跃列表 `m_ids` 中：
    *   如果在：说明修改它的事务还没提交，**不可见**。
    *   如果不在：说明修改它的事务已经提交了，**可见**。

---

#### 5. 当前读与快照读 (中)

在 MVCC 体系下，读取操作分为两种：

1.  **快照读（Snapshot Read）**：
    *   **定义**：普通的、不加锁的 `SELECT` 语句（例如：`SELECT * FROM user WHERE id = 1`）。
    *   **原理**：基于 **MVCC** 机制，读取的是数据的历史版本（快照），不需要加锁，不会被阻塞。
2.  **当前读（Current Read）**：
    *   **定义**：读取的是数据库**最新提交的数据**，并且读取时会对记录**加锁**，防止别人并发修改。
    *   **常见语句**：`UPDATE`、`DELETE`、`INSERT`、`SELECT ... FOR UPDATE`（排他锁）、`SELECT ... LOCK IN SHARE MODE`（共享锁）。

---

#### 6. MVCC 是怎么解决不可重复读的？ (中)

*(注：不可重复读是指一个事务内两次读取同一条数据结果不一样。)*

MVCC 解决不可重复读，关键在于 **ReadView 生成的时机不同**。这涉及 InnoDB 的两种隔离级别：

*   在 **RC（读已提交）** 级别下，事务中**每次**执行 `SELECT` 都会重新生成一个新的 ReadView。所以一旦别的事务提交了修改，新的 ReadView 就能看到，导致不可重复读。
*   在 **RR（可重复读，MySQL 默认）** 级别下，事务**只在第一次**执行 `SELECT` 时生成一个 ReadView。之后该事务内的所有普通查询都**复用这个同一个 ReadView**。
    *   **结论**：因为 ReadView 没变，判断可见性的标准也没变，所以不管别人怎么修改并提交数据，当前事务沿着版本链找出来的数据永远和第一次查出来的一模一样，从而完美解决了**不可重复读**问题。

---

#### 7. MVCC 是怎么防止幻读的？ (高)

面试官问这个问题，其实往往是个"连环套"。严格来说，**单靠 MVCC 是无法彻底防止幻读的**，MySQL InnoDB 在 RR 隔离级别下，是通过 **MVCC + 锁机制** 共同解决幻读问题的。

要分两种场景来回答：

1.  **对于普通查询（快照读）—— 靠 MVCC 解决**：
    在 RR 级别下，事务的第一次 `SELECT` 会生成 ReadView。如果此时别的事务**插入**了一条新数据并提交，由于这条新数据的 `trx_id` 肯定大于 ReadView 的 `max_trx_id`，根据 ReadView 规则，这条新数据对当前事务是**不可见**的。因此，快照读下没有幻读。
2.  **对于加锁查询/修改（当前读）—— 靠 Next-Key Lock（临键锁）解决**：
    如果是 `SELECT ... FOR UPDATE` 或者 `UPDATE` 操作，属于当前读，它会强行读取最新数据，MVCC 就不管用了。
    此时，InnoDB 会使用 **Next-Key Lock（记录锁 + 间隙锁 Gap Lock）**。它不仅会锁住查询出来的行，还会把**行与行之间的"间隙"锁住**。其他事务想在这个间隙里 `INSERT` 新数据会被直接阻塞，从而彻底防止了幻读。

---

### 2.3 锁

---

#### 1. 锁的分类 (中)

*   按锁粒度：表级锁、行级锁、页级锁
*   按使用方式：共享锁（S 锁）、排他锁（X 锁）
*   按加锁机制：悲观锁、乐观锁
*   按锁定范围（InnoDB）：记录锁、间隙锁、临键锁、插入意向锁等

---

#### 2. 共享锁和排他锁 (中)

*   共享锁（S 锁／读锁）：允许其它事务再加 S 锁读取，但不允许加 X 锁修改。
*   排他锁（X 锁／写锁）：不允许其它事务加任何 S 或 X 锁，直到锁释放。
*   兼容性：S 与 S 兼容，S 与 X 不兼容，X 与 X 不兼容。

---

#### 3. 表级锁和行级锁的区别 (中)

*   锁定粒度：表锁锁整张表，行锁只锁相关行。
*   并发性能：表锁并发度低，写操作易阻塞读；行锁并发度高，不同行操作互不干扰。
*   开销：表锁管理简单，开销小；行锁需要更多内存和算法支持，开销更大。
*   死锁：表锁一般不会死锁，行锁可能产生死锁。
*   引擎支持：MyISAM 仅支持表锁；InnoDB 支持行锁和表锁。

---

#### 4. InnoDB 有哪几类行锁？ (中)

*   记录锁（Record Lock）：锁定索引上的单行记录。
*   间隙锁（Gap Lock）：锁定索引记录之间的间隙，防止插入新记录（防止幻读）。
*   临键锁（Next-Key Lock）：记录锁 + 间隙锁的组合，锁定一个左开右闭区间。
*   插入意向锁（Insert Intention Lock）：特殊间隙锁，表示准备在间隙中插入，互不阻塞但会与间隙锁冲突。

---

#### 5. 数据库的表锁和行锁有什么作用？ (中)

*   保证事务的隔离性和数据一致性，避免脏读、不可重复读、幻读等问题。
*   表锁：适合读多写少、简单粗粒度控制，管理方便，但影响并发。
*   行锁：适合高并发读写环境，缩小锁定范围，提高事务吞吐量，减少锁冲突。

---

#### 6. MySQL 两个事务的 update 语句同时更新同一条数据，会发生什么情况？ (中)

*   先到达的 update 会对该行加 X 锁（排他锁）。
*   后到达的 update 请求对该行加 X 锁时，会因冲突进入等待状态，直至前一个事务提交或回滚。
*   若前事务提交，后事务获得锁后继续更新；若回滚，后事务基于最新数据更新。
*   若等待超时或发生死锁，InnoDB 可能回滚其中一个事务。

---

#### 7. 两条 update 语句修改处理同一张表的不同范围的数据，一个 < 5，一个 > 10，会阻塞吗？ (中)

*   **条件字段有索引**：InnoDB 使用行锁及间隙锁。
    *   `< 5` 锁定范围大致为 (-∞, 5) 的记录与间隙。
    *   `> 10` 锁定范围大致为 (10, +∞) 的记录与间隙。
    *   两个范围不重叠，**不会阻塞**。
*   **条件字段无索引**：会导致全表扫描，逐行加锁，可能锁定整张表，此时**会阻塞**。
*   因此，是否阻塞取决于索引使用情况；典型场景下（有索引）不会相互阻塞。

---

## 三、索引与性能优化

---

### 3.1 索引底层与核心机制

---

#### 1. MySQL 中的索引类型 (高)

可以从三个维度来划分：
*   **按数据结构：** B+Tree 索引、Hash 索引、Full-text 全文索引。
*   **按物理存储（核心）：**
    *   **聚簇索引（主键索引）：** 叶子节点保存了**完整的行数据**。一张表只能有一个。
    *   **非聚簇索引（二级索引 / 辅助索引）：** 叶子节点只保存了**索引字段的值和对应的主键值**。一张表可以有多个。
*   **按逻辑功能：** 主键索引（不允许 null）、唯一索引（允许 null，但值唯一）、普通索引、联合索引（组合索引）。

---

#### 2. 为什么 InnoDB 选择 B+ 树？ (高)

这是和其它数据结构对比得出的最优解：
*   **不选 Hash：** Hash 虽快（$O(1)$），但无序，**不支持范围查询**（如 `age > 20`）和排序。
*   **不选 二叉树/红黑树：** 树的层级太深。树的高度决定了磁盘 I/O 的次数，千万级数据时树高可达几十层，磁盘读取慢得让人崩溃。
*   **不选 B 树：** B 树的非叶子节点也存行数据。一页（16KB）能放的节点变少，导致树变高；且不支持范围查询。
*   **选择 B+ 树的优势：**
    1.  **层级极浅：** 非叶子节点只存指针，一页能存上千个指针，千万级数据树高也只有 3 层，**最多只需 3 次磁盘 I/O**。
    2.  **完美支持范围查询：** 所有的行数据都在叶子节点，且叶子节点之间用**双向链表**连接，扫表和区间查询极快。

---

#### 3. 什么是覆盖索引 / 什么是回表 (高)

*   **回表：** 当我们使用**二级索引**查询数据时，由于二级索引的叶子节点只存了"主键值"，如果没有查到我们想要的所有列，MySQL 就必须拿着这个主键值，**回到"聚簇索引（主键树）"中再查一次**，以获取完整的行数据。这个过程叫回表。
*   **覆盖索引：** 指在一个查询中，**索引包含了（覆盖了）所有需要查询的字段的值**。此时直接在二级索引的树上就能拿到全部结果，**无需回表**，极大地提升了查询性能。
    *(面试应对：使用 `EXPLAIN` 查看执行计划，如果 `Extra` 列显示 `Using index`，说明触发了覆盖索引。)*

---

#### 4. 索引下推 (Index Condition Pushdown, ICP) (中)

MySQL 5.6 引入的优化。
假设有联合索引 `(name, age)`，查询 `WHERE name = '张三' AND age > 20`。
*   **没有下推：** 存储引擎先按 `name = '张三'` 在索引树中找到主键，**立刻回表**查出完整行，把行交由 Server 层，再由 Server 层判断 `age > 20`。
*   **有索引下推：** 存储引擎在二级索引树内部寻找 `name = '张三'` 时，**直接根据索引里的 `age` 顺便把 `age > 20` 的记录过滤出来**。过滤完之后再去回表。大大减少了回表的次数。

---

### 3.2 联合索引与设计原则

---

#### 1. 创建联合索引时需要注意什么？ / 什么情况不走联合索引？ (高)

*   **核心法则：最左前缀法则。**
    假设创建了联合索引 `(a, b, c)`，MySQL 是先按 a 排序，a 相同再按 b 排序... 因此查询条件必须**从索引的最左列开始，并且不能跳过中间的列**。
*   **不走联合索引（失效）的场景：**
    1.  **没有 a：** `WHERE b = 1 AND c = 2`（完全失效）。
    2.  **跳过了 b：** `WHERE a = 1 AND c = 2`（只有 a 用到了索引，c 用不到）。
    3.  **遇到范围查询后断崖：** `WHERE a = 1 AND b > 2 AND c = 3`（a 和 b 走索引，但 b 以后（即 c）的字段索引失效）。

---

#### 2. 索引设计原则 (高)

*   **选高频度：** 频繁出现在 `WHERE`、`ORDER BY`、`GROUP BY` 中的字段。
*   **选区分度（基数）高：** 唯一性强的列（如手机号、身份证号）建索引效果好。
*   **尽量用联合索引：** 替代多个单列索引，容易触发覆盖索引，减少回表。
*   **使用前缀索引：** 对于长字符串（如 URL/富文本），只截取前 N 个字符建索引，节省空间。

---

#### 3. 什么时候不要使用索引 (高)

*   数据量极少的表（直接全表扫描更快）。
*   区分度极低的字段（如性别男/女、状态 0/1，加了索引反而比全表扫描还慢）。
*   频繁更新的字段（维护 B+ 树的成本太高）。
*   `WHERE` 中极少使用的字段。

---

#### 4. 索引的优缺点？ (高)

*   **优点：** 极大提高数据检索速度；通过唯一索引保证数据唯一性；加速表与表之间的连接；显著减少查询中分组和排序的时间。
*   **缺点：** 占用磁盘物理空间；降低了表更新（INSERT、UPDATE、DELETE）的速度，因为每次操作都要动态维护 B+ 树。

---

### 3.3 索引失效与慢 SQL 分析

---

#### 1. 索引的使用原则 / 索引失效场景 (高)

*(面试必背 6 大失效场景)*：
1.  **违反最左前缀法则**（针对联合索引）。
2.  **函数或计算运算：** `WHERE YEAR(create_time) = 2023` 或 `WHERE id + 1 = 5` 会导致失效。
3.  **隐式类型转换：** 字符串类型的字段，查询时不加单引号 `WHERE phone = 13800000000`（底层会自动用 CAST 函数转换，导致失效）。
4.  **模糊查询导致失效：** **左模糊或全模糊** `WHERE name LIKE '%张'`（只有右模糊 `LIKE '张%'` 才走索引）。
5.  **OR 语句两边不均衡：** 如果 OR 两边的条件，一边有索引，一边没索引，那么无论如何都会全表扫描。
6.  **优化器认为全表扫描更快：** 数据量少，或者你要查的数据占了全表的很大比例（如查 `!=` 或 `IS NOT NULL`），优化器会直接放弃索引。

---

#### 2. 怎么找到慢 SQL？ / 什么是慢查询日志（slow query log） (高)

*   **慢查询日志：** MySQL 提供的一种日志记录，可以配置 `long_query_time`（比如设为 1 秒或 2 秒）。所有执行时间超过这个阈值的 SQL 都会被自动记录在文件中。
*   **如何找：**
    1.  开启慢查询日志。
    2.  使用 MySQL 自带的 `mysqldumpslow` 工具，或者阿里开源的 Druid 监控平台，找出执行频率最高、耗时最长的 SQL。

---

#### 3. EXPLAIN 执行计划 (高)

在 SQL 前面加上 `EXPLAIN`，可以查看 MySQL 打算如何执行这条 SQL。重点关注 5 个字段：
1.  **`type`（连接类型）：** 性能从好到坏依次是 `system > const` (主键单条查询) `> eq_ref > ref` (普通索引) `> range` (范围查询) `> index` (扫描全索引树) `> ALL` (全表扫描)。**通常要求至少达到 `range` 或 `ref` 级别。**
2.  **`possible_keys`：** 可能用到的索引。
3.  **`key`：** 实际用到的索引。
4.  **`key_len`：** 索引的长度（用来推算联合索引到底用到了哪几列）。
5.  **`Extra`：** 额外信息。看到 `Using index` 是好事（覆盖索引）；看到 `Using filesort`（外部文件排序）或 `Using temporary`（用到临时表）则**必须优化**。

---

#### 4. EXPLAIN 发现执行的索引不正确的话，怎么办？ (高)

*   **为什么不正确：** 优化器是基于统计信息（数据量、区分度）来计算成本的，如果表经常大规模更新，统计信息会过期，导致选错索引。
*   **解决方案：**
    1.  执行 `ANALYZE TABLE 表名;` 重新计算表的统计信息。
    2.  在 SQL 中使用 `FORCE INDEX (索引名)` 强制 MySQL 走指定的索引。
    3.  审查 SQL 逻辑或干脆删除掉那个捣乱的废弃索引。

---

#### 5. 发现查询速度很慢，怎么解决？ (高)

这是一道综合排查题，回答要有层次感（SOP）：
1.  **确认问题：** 观察数据库 CPU/内存负载，确认是单条 SQL 慢还是整体慢。
2.  **抓取 SQL：** 通过慢查询日志抓取耗时最长的 SQL。
3.  **EXPLAIN 分析：** 看是否全表扫描、是否没走索引、是否发生了 `filesort`。
4.  **优化手段：**
    *   **加索引 / 调索引：** 增加联合索引，实现覆盖索引。
    *   **改写 SQL：** 避免 `select *`，小表驱动大表，优化深度分页。
    *   **架构层面优化：** 如果单表过大（千万级以上），考虑分库分表、或者把查询迁移到 Redis 缓存、Elasticsearch 搜索引擎中。

---

### 3.4 SQL 优化细节

---

#### 1. 常见 SQL 优化手段 / 各种子句优化 (高)

*   **主键优化：** 主键一定要**短小、自增、按顺序插入**。不要用 UUID 作主键！因为无序的主键在插入时会导致 B+ 树频繁发生"**页分裂**"，极度消耗 I/O 并产生内存碎片。
*   **插入优化 (Insert)：**
    1.  使用批量插入 `INSERT INTO t VALUES (),(),()`；
    2.  手动开启和提交事务，避免每插入一条就开启一次事务；
    3.  按主键顺序插入。
*   **Update 优化：** **更新语句的 `WHERE` 条件一定要走索引！** 否则 InnoDB 会将行级锁升级为**表级锁**，导致整张表在更新期间无法被其他人写入。
*   **Order By 优化：**
    1.  尽量让排序的字段被索引覆盖，通过索引直接返回有序数据（`Using index`），避免在内存或磁盘中二次排序（`Using filesort`）。
    2.  多个字段排序时，严格遵循联合索引的最左前缀，且 ASC/DESC 规则要与索引创建时保持一致。
*   **Group By 优化：** 在被分组的列上建立索引，这样 MySQL 就不需要创建内部临时表来分组了。
*   **Where 优化：** 把最容易过滤掉大部分数据的条件放在前面（虽然优化器会自动调整，但代码更清晰）；杜绝在 where 里写函数。

---

#### 2. Limit 优化（深分页问题） (高)

*   **痛点：** `LIMIT 1000000, 10`。MySQL 会傻傻地把前 1000010 条数据从磁盘读出来，然后扔掉前 100 万条，只返回最后 10 条。极其慢！
*   **优化（延迟关联法）：**
    利用覆盖索引先快速查出那一页数据的**主键 ID**，然后再拿这 10 个 ID 用 `JOIN` 去原表捞取完整数据。

    ```sql
    SELECT t1.* FROM 原表 t1
    JOIN (SELECT id FROM 原表 WHERE 条件 LIMIT 1000000, 10) t2
    ON t1.id = t2.id;
    ```

---

#### 3. 几种 Count 对比 (高)

面试官非常喜欢问 `count(*)`、`count(1)`、`count(主键)` 和 `count(字段)` 哪个快。
*   **性能排序：** `count(*)` ≈ `count(1)` > `count(主键)` > `count(字段)`。
*   **原理：**
    *   **`count(字段)`：** 最慢。要扫表，还要判断该字段是否为 NULL（不统计 NULL）。
    *   **`count(主键)`：** 遍历整棵主键索引树，提取所有主键给 Server 层进行累加计算。
    *   **`count(1)`：** 不取数据，遍历索引树，每遇到一行就放一个数字"1"进去累加，比取主键快一点点。
    *   **`count(*)`：** MySQL 专门对 `count(*)` 做了极致优化！它不会把全部字段取出来，而是**专门找一棵数据量最小的二级索引树**进行遍历。在 InnoDB 层面只要有行就算进去，不进行任何值的解析，所以是**最快**的。

## 四、日志系统

---

#### 1. 三大日志概述 (高)

MySQL InnoDB 存储引擎涉及三类关键日志：
*   **redo log（重做日志）**：物理日志，记录数据页的修改，用于崩溃恢复，保证事务的持久性。
*   **undo log（回滚日志）**：逻辑日志，记录数据修改前的版本，用于事务回滚和 MVCC，保证事务的原子性。
*   **binlog（二进制日志）**：逻辑日志，记录所有可能引起数据变更的 SQL 或行变化，用于主从复制和基于时间点的数据恢复。

其中 redo log 和 undo log 属于 InnoDB 引擎层，binlog 属于 MySQL Server 层。

---

#### 2. binlog 主要记录了什么？有什么用？ (高)

*   **记录内容**
    binlog 记录所有对数据库产生修改的操作（DDL、DML），以事件形式保存。它属于逻辑日志，有三种格式：
    *   `STATEMENT`：记录 SQL 语句。
    *   `ROW`：记录每一行数据的变更情况（推荐）。
    *   `MIXED`：混合模式，多数用 STATEMENT，需要时自动切换为 ROW。

*   **主要用途**
    1.  **主从复制**：从库通过拉取主库 binlog 进行重放，实现数据同步。
    2.  **数据恢复**：利用全量备份配合 binlog 重放，可以将数据库恢复到任意时间点。
    3.  **审计与数据迁移**：某些审计工具、异构数据同步工具会解析 binlog 获取变更流。

---

#### 3. redo log 主要记录了什么？有什么用？ (高)

*   **记录内容**
    redo log 是 **物理日志**，记录的是"对某个数据页做了什么物理修改"，比如"页 XXX 偏移量 YYY 写入值 ZZZ"。它以日志块的方式顺序写入，关联数据页的物理变化。

*   **主要用途**
    **崩溃恢复（Crash Recovery）**：当数据库突然崩溃，内存中的脏页丢失，重启时依靠 redo log 将已提交但未刷盘的事务修改重新应用到磁盘，从而保证已提交事务的持久性（Durability）。

---

#### 4. redo log 基本过程 (高)

1.  **修改记录**
    在 Buffer Pool 中修改数据页前，先生成对应的 redo log，写入 redo log buffer（内存中）。
2.  **事务提交刷盘**
    事务提交时，根据 `innodb_flush_log_at_trx_commit` 设定将 redo log buffer 刷到磁盘的 redo log 文件：
    *   `1`：每次提交都刷盘（默认，最安全，持久性最高）。
    *   `0`：每秒刷一次，提交时不强制刷。
    *   `2`：每次提交都写到操作系统缓存，每秒刷盘。
3.  **日志顺序写**
    redo log 文件采用固定大小、循环写的方式（一组文件，写完第一个再写第二个），写入点为 `Log Sequence Number (LSN)` 不断增长。
4.  **脏页刷盘**
    已提交事务的脏页由后台线程（如 Master Thread）在适当时候刷回磁盘，它比 redo log 写入慢得多（随机写）。
5.  **崩溃恢复**
    重启时，InnoDB 扫描 redo log，重放所有已提交但尚未刷盘的日志记录，将数据页恢复到最新状态（前滚）。

---

#### 5. 为什么事务提交后不直接将 Buffer Pool 的数据同步到磁盘？ (中)

*   **磁盘 IO 方式的巨大差异**
    Buffer Pool 中脏页的磁盘写入是 **随机写**，通常涉及多次寻道，性能极差；而 redo log 是 **顺序写**，性能远超随机写。
*   **减少磁盘写入次数**
    同一数据页可能被多个事务多次修改，如果每次提交都刷脏页，会产生大量重复的磁盘 IO。redo log 仅记录每次修改的物理日志，多次修改只需一次顺序写日志，脏页可以稍后统一刷盘（合并写入）。
*   **保证高性能与持久性平衡**
    通过"WAL（Write-Ahead Logging）"技术，事务提交只需保证 redo log 写入磁盘，无需等待脏页刷盘，既实现了持久性，又极大提升了事务吞吐量。

---

#### 6. binlog 和 redo log 有什么区别？ (中)

| 区别点 | redo log | binlog |
| --- | --- | --- |
| **产生层** | InnoDB 引擎层产生 | MySQL Server 层产生，与存储引擎无关 |
| **日志类型** | 物理日志，记录数据页的物理修改 | 逻辑日志，记录 SQL 语句或行变更（ROW 格式） |
| **写入方式** | 固定大小、循环写（写满会覆盖旧日志，需配合脏页刷盘） | 追加写，单个文件写满后可切换新文件，不会覆盖 |
| **用途** | 崩溃恢复，保证已提交事务的持久性 | 主从复制、数据恢复（PITR）、审计等 |
| **落盘时机** | 事务提交时（由 `innodb_flush_log_at_trx_commit` 控制） | 事务提交时写入（由 `sync_binlog` 控制是否立即刷盘） |
| **崩溃恢复** | 用于前滚已提交事务 | 不直接用于引擎崩溃恢复（binlog 仅用于复制和恢复场景） |

---

#### 7. 为什么需要 redo log (高)

1.  **避免随机写，实现顺序写加速**
    如果没有 redo log，为保证持久性，每次事务提交必须把随机位置的脏页刷盘，这会导致极高的磁盘寻道和写入延迟。redo log 将随机写转化为顺序写，大幅度提升写入性能。
2.  **WAL 技术的核心**
    通过"先写日志，再刷脏页"的策略，事务提交的持久性仅依赖 redo log 的落盘，脏页可在后台异步批量写入，实现了数据持久性与高性能的统一。
3.  **崩溃恢复的必要手段**
    断电或异常崩溃后，内存中的脏页丢失，redo log 能够精确重演已提交的修改，将数据库恢复到崩溃前的完整性状态。没有 redo log，提交过的事务就会丢失，无法满足 ACID 的持久性。

---

#### 8. 两阶段提交是什么？ (中)

两阶段提交（2PC）用于保证 **redo log** 与 **binlog** 的逻辑一致性，防止主从数据不一致。以事务提交为例：

*   **Prepare 阶段**：
    事务执行完后，先写入 redo log 并标记为 `PREPARE` 状态（此时不提交）。
*   **Commit 阶段**：
    1.  将事务的 binlog 写入磁盘（`sync_binlog`）。
    2.  将 redo log 从 `PREPARE` 状态改为 `COMMIT` 状态，事务提交完成。

**崩溃恢复判断逻辑**：
*   如果 redo log 处于 `PREPARE` 状态，且 binlog 中存在对应事务 → 提交该事务。
*   如果 redo log 处于 `PREPARE` 状态，但 binlog 中不存在该事务 → 回滚该事务。

这样，无论何时崩溃，redo log 和 binlog 总能保持一致，从库通过 binlog 重放的数据也与主库最终一致。

---

#### 9. undo log (高)

*   **记录内容**
    undo log 是 **逻辑日志**，记录事务修改前的数据"旧版本"。例如，插入一条记录，undo log 会记录删除该记录的信息；更新一条记录，undo log 记录更新前的原值。
*   **主要作用**
    1.  **事务回滚（原子性）**：执行 `ROLLBACK` 时，利用 undo log 将数据恢复到事务开始前的状态。
    2.  **多版本并发控制（MVCC）**：一致性非锁定读（如 `REPEATABLE READ` 下的快照读）通过 undo log 构建历史版本，实现读不阻塞写，提高并发性能。
*   **与 redo log 的关系**
    undo log 本身的修改（即写入 undo 页）也会生成 redo log，从而保护 undo log 的持久性，确保回滚在崩溃后依然有效。
*   **生命周期**
    undo log 在事务开启时产生，事务提交后并不会立刻清除，而是保留至不再有任何事务需要看到其历史版本（由 Purge 线程统一清理）。
