### 1. JVM 内存结构（高）

JVM 内存结构主要分为以下几个部分：

- **堆**：所有线程共享，存放对象实例和数组。是垃圾回收的主要区域，可细分为新生代和老年代。
- **方法区**：所有线程共享，存储类信息、常量、静态变量、即时编译器编译后的代码缓存等。
- **虚拟机栈**：线程私有，每个方法执行时创建一个栈帧，存储局部变量表、操作数栈、动态链接、方法返回地址等。
- **本地方法栈**：线程私有，与虚拟机栈类似，但服务于本地方法。
- **程序计数器**：线程私有，记录当前线程执行的字节码行号。

---

### 2. 线程私有 vs 线程共享（高）

- **线程私有**：虚拟机栈、本地方法栈、程序计数器。
- **线程共享**：堆、方法区。

---

### 3. 堆和栈的区别（高）

| 对比项         | 堆                         | 栈                                               |
| -------------- | -------------------------- | ------------------------------------------------ |
| **存储内容**   | 对象实例、数组             | 局部变量表、操作数栈、方法返回信息               |
| **线程共享性** | 所有线程共享               | 每个线程独立私有                                 |
| **生命周期**   | 随应用运行存在，由 GC 回收 | 与线程同生命周期，方法调用创建栈帧，方法结束弹出 |
| **分配方式**   | 动态分配，内存不连续       | 静态分配或动态分配，内存连续                     |
| **性能**       | 较慢，存在并发竞争         | 极快，无需同步                                   |
| **异常**       | `OutOfMemoryError`         | `StackOverflowError` 或 `OutOfMemoryError`       |

---

### 4. 常见问题（中）

- **垃圾回收是否涉及栈内存？** 不涉及。栈内存由编译器自动管理，方法结束时栈帧自动弹出释放，无需 GC。
- **栈内存分配越大越好吗？** 不是。栈内存越大，可分配线程数越少（每个线程有独立栈），反而容易 OOM。
- **方法内的局部变量是否线程安全？** 基本类型是安全的。若变量引用对象且对象逃逸出方法，则可能不安全。
- **如何判断线程安全？** 看变量是否发生逃逸。若仅在方法内使用（无 return、无外部引用传递），则由逃逸分析标记为线程安全。反之，若对象可被其他线程访问，则存在安全风险。

---

### 5. 大对象一般在哪个区域？（中）

通常直接分配在**老年代**。当对象大小超过 `-XX:PretenureSizeThreshold`（通常为 3MB）时，直接进入老年代，避免在新生代的 Eden 区和 Survivor 区之间频繁拷贝。

---

### 6. 字符串常量池是什么（中）

字符串常量池是 JVM 为字符串开辟的特殊存储区，用于缓存编译期生成的或调用 `intern()` 的字符串，避免重复创建相同内容的字符串对象。

- **JDK 7 之前**：位于方法区。
- **JDK 7 及之后**：移至堆中，方便 GC 回收。

---

### 7. 什么是零拷贝（中）

零拷贝是一种 I/O 优化技术，指 CPU 不需要将数据从内核空间复制到用户空间（或减少拷贝次数），而是直接将数据从磁盘或网卡传输到另一端。常见实现：

- **sendfile**：数据不经过用户态，直接在内核空间进行文件到套接字的传输。
- **mmap**：将文件映射到内存，用户态可直接访问，减少一次拷贝。

---

### 8. 内存泄漏和内存溢出的区别（高）

- **内存泄漏**：对象已无用但依然被 GC Root 引用，无法回收，占用的内存越积越多。
- **内存溢出**：JVM 没有足够空闲内存分配新对象，抛出 `OutOfMemoryError`。内存泄漏是导致溢出的常见原因。

---

### 9. 内存溢出的几种情况（中）

- **堆溢出**：对象创建过多，`-Xmx` 不足。如 `java.lang.OutOfMemoryError: Java heap space`。
- **栈溢出**：线程请求栈深度超过 JVM 允许的最大深度（如递归过深），抛出 `StackOverflowError`。
- **方法区溢出**：加载类过多或常量池过大（如动态代理类），抛出 `OutOfMemoryError: Metaspace`。
- **直接内存溢出**：使用 NIO 的 `ByteBuffer.allocateDirect` 分配过多堆外内存，抛出 `OutOfMemoryError: Direct buffer memory`。

---

### 10. JVM 的主要组成部分及其作用（中）

1. **类加载器**：加载字节码文件到 JVM。
2. **运行时数据区**：包括堆、方法区、虚拟机栈、本地方法栈、程序计数器，负责存储与执行。
3. **执行引擎**：解释字节码，或通过即时编译器编译为机器码后执行。
4. **本地方法接口（JNI）**：供 Java 调用 C/C++ 等本地库。
5. **即时编译器（JIT）**：将热点字节码编译为本地机器码，提升性能。
6. **垃圾回收器**：自动管理堆内存，回收不再使用的对象。

---

### 11. 强引用、软引用、弱引用、虚引用（中）

| 引用类型   | 回收时机                                                     | 用途                               |
| ---------- | ------------------------------------------------------------ | ---------------------------------- |
| **强引用** | 绝不回收，直到没有 GC Root 指向                              | 普通对象引用                       |
| **软引用** | 内存不足时回收                                               | 实现内存敏感缓存                   |
| **弱引用** | 每次 GC 时回收（无论内存是否充足）                           | `WeakHashMap`、ThreadLocal         |
| **虚引用** | 任何 GC 时回收，无法单独获取对象，必须与 ReferenceQueue 联合使用 | 跟踪对象回收状态（如管理直接内存） |

- **虚引用的区别**：无法通过 `get` 获得对象，必须与引用队列配合，用于对象回收时的后处理。
- **软引用的好处**：可以实现缓存，在即将 OOM 之前自动释放，兼顾性能与内存安全。

## 垃圾回收

### 12. 垃圾回收算法是什么，为了解决了什么问题？（高）
垃圾回收算法是自动管理内存的机制，用于识别并回收不再被程序使用的对象所占用的内存空间。它主要解决：
- **内存泄漏**：手动管理内存时容易遗忘释放，导致可用内存不断减少。
- **悬空指针**：释放内存后未置空指针，后续误用会导致崩溃或不安全访问。
- **碎片化**：多次分配与释放后内存空间不连续，大对象分配失败。
- **开发负担**：将开发者从繁琐的手动内存管理中解放出来，专注于业务逻辑。

---

### 13. 如何判断对象是否死亡 / 如何判断对象可以被回收（高）
**引用计数法**
- 对象中维护一个引用计数器，每当有地方引用它时加1，引用失效时减1。
- 计数器为0的对象不可再被使用，可回收。
- 缺点：无法解决循环引用问题（A引用B，B引用A，计数器都不为0，但两者实际已无外部引用）。

**可达性分析（根搜索算法）**
- 从一组被称为 **GC Roots** 的根对象开始，向下搜索引用链。
- 若对象与 GC Roots 之间没有任何引用链（引用链不可达），则该对象被判定为可回收。
- 常见 GC Roots 包括：虚拟机栈中引用的对象、方法区静态属性引用的对象、常量引用的对象、JNI引用的对象等。

---

### 14. 垃圾收集有哪些算法，各自的特点？（高）
**标记-清除算法**
- 分标记和清除两阶段：先标记所有可达对象，再统一清除未标记对象。
- 优点：不需要移动对象，实现简单。
- 缺点：产生大量不连续内存碎片；标记和清除效率都不高。

**标记-整理（标记-压缩）算法**
- 标记过程与标记-清除相同，清除时将存活对象向一端移动，然后清理边界外的内存。
- 优点：消除内存碎片。
- 缺点：移动对象需要更新引用，成本较高，需STW暂停。

**复制算法**
- 将内存分为两块，每次只使用其中一块。GC时将存活对象复制到另一块，然后整体清理原空间。
- 优点：无碎片，分配速度快（只需移动指针）。
- 缺点：可用内存缩小一半；对象存活率高时复制成本变大。

---

### 15. 分代收集算法（高）
根据对象生命周期不同，将堆划分为新生代和老年代，分别采用最合适的收集算法。

**新生代**
- 对象死亡率高（朝生夕灭），使用**复制算法**。
- 分为一块较大的 Eden 区和两块较小的 Survivor 区（默认比例 8:1:1）。
- 每次回收时将 Eden 和 From Survivor 中存活对象复制到 To Survivor，然后清理 Eden 和 From。

**老年代**
- 对象存活率高，没有额外空间担保，使用**标记-清除**或**标记-整理**算法。

---

### 16. 常见的垃圾回收器有哪些？（中）
**串行收集器**
- Serial / Serial Old：单线程工作，GC 时必须暂停所有用户线程（STW）。
- 适合单核 CPU、内存小的客户端应用。

**并行收集器**
- Parallel Scavenge / Parallel Old：多线程收集，关注吞吐量，仍然需要 STW，但 GC 时间较短。
- 适合后台计算、科学运算等注重吞吐的场景。

**并发收集器**
- CMS（Concurrent Mark Sweep）：以最短 STW 为目标，用户线程与 GC 线程并发执行。
- G1（Garbage First）：采用区域化分片，可控制停顿时间，并发标记与筛选回收。
- ZGC/Shenandoah：超低延迟（<10ms），采用染色指针等新技术。

---

### 17. 介绍一下 CMS（高）
CMS（Concurrent Mark Sweep）是一种以获取最短回收停顿时间为目标的收集器，基于标记-清除算法，主要用于老年代。
**过程：**
1. 初始标记（STW）：仅标记 GC Roots 能直接关联到的对象。
2. 并发标记：与用户线程并发，遍历整个对象图。
3. 重新标记（STW）：修正并发标记期间因用户线程运行导致变动的对象。
4. 并发清除：与用户线程并发，清理标记的垃圾对象。
**缺点**：
- 占用 CPU 资源，减少吞吐量。
- 浮动垃圾（并发清除期间产生的垃圾无法回收，留到下次GC）。
- 基于标记-清除，会产生内存碎片，可能触发 Full GC。

---

### 18. 介绍一下 G1（高）
G1（Garbage-First）将堆划分为大小相等的 Region，兼顾新生代和老年代，可预测停顿时间。
**过程：**
1. 初始标记（STW）。
2. 并发标记。
3. 最终标记（STW）。
4. 筛选回收（STW）：根据用户期望的停顿时间，优先回收垃圾最多的 Region。
**特点**：
- 空间整合，整体基于标记-整理，局部基于复制，无碎片。
- 可控的停顿模型，通过设置 `-XX:MaxGCPauseMillis` 指定期望值。
- 跨 Region 引用通过记忆集（Remembered Set）解决。

---

### 19. 什么是三色标记算法（中）
三色标记法是一种用于并发标记的算法，将对象分为三种颜色：
- **白色**：尚未被标记的对象，GC 结束时为不可达，将被回收。
- **灰色**：对象已被标记，但其引用的子对象尚未全部扫描。
- **黑色**：对象及所有引用都已扫描完毕，是存活对象。
过程：初始所有对象为白色，将 GC Roots 置灰并放入灰色队列，然后不断从灰色队列取出对象，将其引用子对象置灰，自身变黑，直到灰色队列为空。剩余的白色对象即为垃圾。

---

### 20. 三色标记存在问题（中）
并发标记时用户线程可能修改引用关系，导致两种问题：
- **多标**：原本被标记为存活的对象，之后失去引用变为垃圾（浮动垃圾）。影响较小，下次 GC 回收。
- **漏标**：应当被标记的对象被遗漏为白色，导致存活对象被错误回收。需要破坏两个条件之一：插入新引用时记录，或删除引用时记录。CMS 和 G1 分别用**写后屏障**（SATB）或**写屏障**来处理增量更新。

---

### 21. G1的记忆集RSet与卡表（低）
- **卡表**：老年代内存被分成固定大小（512字节）的卡片，当某个卡片内的对象引用发生变化，该卡片被标记为“脏”。G1 维护 Remembered Set（RSet）来记录每个 Region 被哪些卡表指向。
- **RSet**：每个 Region 有一个 RSet，记录其他 Region 对本 Region 的引用信息。是一种抽象数据结构，用于避免全堆扫描。当进行 Young GC 或 Mixed GC 时，只需扫描对应 RSet 即可找到外部根引用。

---

### 22. 如何选择垃圾收集器（中）
- **小内存，单核**：Serial。
- **注重吞吐量**：Parallel Scavenge + Parallel Old。
- **低延迟，JDK8**：CMS（但碎片化和浮动垃圾要注意）。
- **低延迟，大堆，JDK8+**：G1（可控停顿）。
- **超低延迟（<10ms），JDK11+**：ZGC 或 Shenandoah。
同时还要结合硬件资源、堆大小、应用特征综合选择。

---

### 23. 什么情况下使用CMS，什么情况使用G1？（中）
- **CMS**：适合老年代较小（<4G）、对停顿时间要求较高但能容忍偶尔的长暂停的场景。若内存碎片严重可能触发 Full GC。
- **G1**：适合大堆（>4G）、要求可预测停顿时间（<200ms）的场景。通过 Region 和 RSet 进行细粒度控制，适合对延迟敏感的 Web 应用。

---

### 24. G1回收器的特色是什么？（中）
- **区域化内存布局**：取消固定的新生代/老年代，采用大小相等的 Region。
- **可预测停顿**：通过 `-XX:MaxGCPauseMillis` 设置目标，G1 会尽量满足。
- **筛选回收**：优先回收垃圾最多的 Region（Garbage-First），效率高。
- **并发与并行**：标记阶段并发，回收阶段多线程并行，减少 STW。
- **空间整合**：使用复制+标记-整理，无内存碎片。

---

### 25. Minor GC 和 Full GC 有什么不同呢？Minor GC与Full GC分别在什么时候发生？（高）
- **Minor GC**：针对新生代的垃圾回收。Eden区满时触发，速度快，频率高，但会产生 STW。
- **Full GC**：针对整个堆（新生代+老年代+方法区）的回收。速度慢，STW时间长，应尽量避免。

---

### 26. 什么时候会触发Full GC（高）
- 调用 `System.gc()`（只是建议）。
- 老年代空间不足（如大对象直接进入老年代，但剩余空间不足）。
- 方法区/元空间不足。
- CMS GC 时出现 `Concurrent Mode Failure`（浮动垃圾太多）或晋升失败（老年代碎片化无法容纳新晋升对象）。
- Minor GC 时检查到要晋升到老年代的对象平均大小 > 老年代剩余空间（空间分配担保失败）。

## 类加载

### 27. 什么是类加载器？常见的类加载器？（中）

**类加载器（ClassLoader）** 是 JVM 中负责将字节码文件（`.class`）加载到内存，并生成对应的 `Class` 对象的组件。它是实现 Java 动态加载和运行时类型判断的基础。

**常见的类加载器（JDK 8 及之前）**：

1. **Bootstrap ClassLoader（启动类加载器）**  
   - 由 C++ 实现，是 JVM 的一部分。  
   - 负责加载 `<JAVA_HOME>/jre/lib` 下的核心类库（如 `rt.jar`、`charsets.jar` 等），或被 `-Xbootclasspath` 指定的路径。  
   - 在 Java 代码中无法直接获取其引用，通常用 `null` 表示。

2. **Extension ClassLoader（扩展类加载器）**  
   - 由 `sun.misc.Launcher$ExtClassLoader` 实现。  
   - 负责加载 `<JAVA_HOME>/jre/lib/ext` 目录下的扩展 jar 包，或被 `java.ext.dirs` 系统变量指定的路径。

3. **Application ClassLoader（应用类加载器）**  
   - 由 `sun.misc.Launcher$AppClassLoader` 实现。  
   - 负责加载用户类路径 `classpath` 上的所有类（即我们日常编写的代码和第三方依赖）。  
   - 是程序中默认的类加载器。

**JDK 9 及之后的变化**：  
由于模块化（JPMS）的引入，扩展类加载器被 **Platform ClassLoader（平台类加载器）** 取代，启动类加载器也更改为仅加载核心模块，但整体双亲委派架构保留。

---

### 28. 双亲委派模式（高）

**定义**  
双亲委派模式（Parents Delegation Model）是 Java 类加载器的一种层次化协作机制：一个类加载器在收到加载类的请求时，首先不会自己尝试加载，而是把请求委托给父类加载器依次向上，直到最顶层的启动类加载器。当父类加载器反馈无法完成加载时，子加载器才会尝试自己加载。

**工作流程**  
1. 自定义类加载器或应用类加载器收到加载请求。  
2. 检查该类是否已经被加载过（在缓存中查找）。  
3. 若未加载，则调用父类加载器的 `loadClass()` 方法，将请求向上委派。  
4. 父类加载器同样先检查缓存，再委派给自己的父类，直到启动类加载器。  
5. 启动类加载器尝试在核心库中加载，如果找不到，则返回子类加载器逐层尝试。  
6. 最终由发起请求的类加载器尝试通过 `findClass()` 自行加载（如从文件系统、网络等读取字节码）。  

**优点**  
- **避免类的重复加载**：全盘由父类加载器保证核心类的唯一性。  
- **保护核心类库安全**：防止用户自定义的 `java.lang.String` 等类替换核心库中的类，杜绝安全隐患。

**核心代码**（`java.lang.ClassLoader` 中的 `loadClass` 方法）：  
```java
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2. 先委托父类加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父类加载器无法加载
            }
            if (c == null) {
                // 3. 父类无法加载，自己加载
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}
```

---

### 29. 为什么要打破双亲委派模型（高）

虽然双亲委派模型保证了类加载的安全性和唯一性，但在某些场景下它的“向上委派”机制会限制灵活性，因此需要打破。

**打破的原因与典型场景**：

**1. 基础类型需要调用用户代码**  
JVM 的核心类库（如 JDBC 接口 `java.sql.Driver`）由启动类加载器加载，但其具体实现（如 MySQL 驱动）却是由应用类加载器加载的。按双亲委派，启动类加载器无法向下委派找到实现类，因此 JDK 引入了 **线程上下文类加载器（Thread Context ClassLoader）**，默认是应用类加载器，使核心库能够反向委托应用类加载器加载具体实现，从而“打破”了单向的委派层次。

**2. 类隔离与模块热部署**  
应用服务器（如 Tomcat、OSGi）需要同时部署多个 Web 应用，每个应用可能依赖不同版本的同一类库。如果使用统一的父类加载器，会出现版本冲突。  
- **Tomcat**：为每个 Web 应用提供独立的 `WebAppClassLoader`，优先自己加载，只有找不到时才向父类加载器请求，而不是先向上委派。  
- **OSGi**：采用网状结构的类加载器，每个模块（Bundle）有自己的类加载器，按精确的导入导出关系协作，完全抛弃了传统的树状双亲委派。

**3. 代码生成与动态代理**  
大量框架（Spring AOP、MyBatis 等）通过动态生成字节码创建类，这些类在运行时由自定义的类加载器直接加载，传统委派模型无法满足其实时性和隔离性需求。

**4. SPI 机制**  
Java 的 SPI（Service Provider Interface）要求接口由核心库定义，但实现由第三方 jar 提供，必须通过线程上下文类加载器等手段反向加载，本质上就是一种对双亲委派的破坏。

## JVM调优

### 常见指标和合理配置
- **吞吐量**：用户代码运行时间占总运行时间的比例，批处理系统要求高吞吐。
- **停顿时间**：单次 GC 造成的应用暂停时间，交互式系统要求低延迟。
- **内存占用**：JVM 进程占用的物理内存，受机器限制需合理配置。
- **GC 频率**：Minor GC 和 Full GC 的发生频率，频率过高会消耗 CPU 并影响响应。

合理配置需根据应用特征在上述三者间平衡，通常通过以下参数实现：
- 堆内存初始/最大一致（`-Xms` = `-Xmx`），避免动态调整开销。
- 新生代大小设置为堆的 1/4～1/3。
- 元空间设置合理初始值，避免频繁扩容。
- 选择合适的垃圾回收器并根据期望目标调优。

### 合理的JVM参数（示例）
```bash
-Xms4g -Xmx4g
-Xmn2g (或 -XX:NewRatio=2)
-XX:SurvivorRatio=8
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=256m
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/gc.log
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/dump
```
以上适用于 4GB 堆的 Web 服务，可根据实际调整。

### JVM 内存指标
- **堆内存使用量**：`HeapMemoryUsage`（`used`、`committed`、`max`）。
- **新生代使用量**：`Eden Space` + `Survivor Space`。
- **老年代使用量**：`Old Gen`（或 G1 的 `Heap Region` 总体）。
- **元空间使用量**：`Metaspace`（`used`、`committed`、`max`）。
- **直接内存**：`DirectBuffer` 监控（通常通过 JMX 或 NMT）。

### JVM GC指标
- **Young GC 次数与耗时**：`jstat -gc` 中的 `YGC`、`YGCT`。
- **Full GC 次数与耗时**：`FGC`、`FGCT`。
- **GC 原因**：从 GC 日志中分析（如 `Allocation Failure`、`G1 Evacuation Pause`、`System.gc()` 等）。
- **晋升情况**：Young GC 后 Survivor 区存活大小、晋升到老年代的对象大小。
- **GC 暂停时长分布**：最大暂停时间、平均暂停时间。

### 调优思路
1. **明确目标**：高吞吐还是低延迟？是否可容忍偶尔长时间停顿？
2. **收集基线**：运行压测或观察线上，收集 GC 日志、堆 dump 和监控数据。
3. **分析瓶颈**：检查是 Young GC 频繁、Young GC 时间过长还是 Full GC 频繁。
4. **调整参数**：优先调整堆大小、代比例、回收器选择，再微调回收器内部参数。
5. **验证与迭代**：每次只改一个主要参数，对比前后指标，逐步逼近最优。

### YGC频繁
**原因**：新生代太小，Eden 区很快被填满；或对象分配速率过高。  
**解决**：
- 增大新生代（`-Xmn`）或增大堆并保持比例（`-XX:NewRatio`）。
- 若是短命对象过多，可优化代码减少分配。
- 若使用 G1，可增大 `-XX:G1HeapRegionSize` 以减少 Young GC 频率，或调整 `-XX:MaxGCPauseMillis`。

### Young GC 时间过长
**原因**：新生代太大，导致每次复制存活对象的成本高；或 Survivor 区过小，大量对象被迫晋升反而引起停顿；存活对象本身很多。  
**解决**：
- 减小新生代大小（但可能增加 YGC 频率，要平衡）。
- 调整 Survivor 比例（`-XX:SurvivorRatio`），增大 Survivor 空间，让对象在新生代多存活几轮，避免过早晋升。
- 使用 G1 回收器，通过 `-XX:MaxGCPauseMillis` 控制期望暂停时间，G1 会自适应调整新生代大小。
- 若是 Parallel GC，可尝试切换为 G1。

### Full GC 频繁
**原因**：
- 老年代空间不足：老年代太小或对象过早晋升。
- 内存泄漏：老年代对象持续增长不可回收。
- 大对象直接进入老年代：`-XX:PretenureSizeThreshold` 设置过小。
- CMS 并发失败：并发清理时浮动垃圾过多，或内存碎片化。
- 元空间不足触发 Full GC（会连带清理老年代）。
- `System.gc()` 显式调用。

**解决**：
- 增大老年代（通过增大堆或调整 `-XX:NewRatio`）。
- 检查内存泄漏，导出 heap dump 分析。
- 调整晋升阈值 `-XX:MaxTenuringThreshold`，控制对象何时进入老年代。
- 对于大对象，可设置合理的 `-XX:PretenureSizeThreshold`（通常不推荐，或者增大）。
- 若是 CMS 频繁出现 `Concurrent Mode Failure`，可降低 `-XX:CMSInitiatingOccupancyFraction`（如 60），提前触发 CMS。
- 使用 G1 替换 CMS，G1 不会产生碎片，且能更平滑地处理老年代回收。
- 显式禁用 `System.gc()`：`-XX:+DisableExplicitGC`。

### 垃圾回收器的选择
- **Serial/SerialOld**：单线程，适合客户端应用，堆小于 1GB，对停顿无要求。
- **Parallel Scavenge / Parallel Old**：多线程，关注吞吐量，适合批处理、科学计算等。
- **CMS**：以低延迟为目标，老年代并发回收，但会产生碎片，CPU 消耗较高，JDK 9 后废弃，不推荐新系统使用。
- **G1**：大堆（>4GB）首选，延迟可控，无碎片，平衡吞吐量与停顿，JDK 9 后默认。
- **ZGC/Shenandoah**：超低延迟（<1ms），适合大堆（>16GB）且对暂停极度敏感的场景，JDK 11/12+。

### CMS调优要点
- 开启参数：`-XX:+UseConcMarkSweepGC`（新生代自动搭配 ParNew）。
- 老年代使用率达到 `-XX:CMSInitiatingOccupancyFraction`（默认 65~70）时启动并发标记。
- 避免并发失败：调低该阈值，给浮动垃圾留足空间。
- 启用碎片整理：`-XX:+UseCMSCompactAtFullCollection`（Full GC 时压缩），并设置 `-XX:CMSFullGCsBeforeCompaction`（多少次 Full GC 后压缩一次）。
- 启用并行重新标记：`-XX:+CMSParallelRemarkEnabled`。

### G1调优要点
- 核心参数：`-XX:MaxGCPauseMillis`，G1 会自动调整新生代大小和回收集来尽量满足该目标（例如 200ms）。
- Region 大小：`-XX:G1HeapRegionSize`，堆较大时可适当增大以减少卡表扫描成本。
- 并发 GC 线程数：`-XX:ConcGCThreads`，一般设置为 CPU 核数的 1/4。
- 防止 Full GC：G1 在并发周期失败或晋升失败时会退化为串行 Full GC，应增大 `-XX:G1ReservePercent`（保留空间，默认 10%），或增大堆。
- 若 Mixed GC 耗时过长，可调整 `-XX:G1MixedGCCountTarget`（默认为 8，增加次数减少每次回收量），或 `-XX:G1HeapWastePercent`（混合回收允许的垃圾比例，默认 5%）。
