# JUC 并发编程八股文（优化版）

---

## 一、线程基础

---

**聊聊线程和进程（高）**

- **进程**：操作系统资源分配的基本单位。拥有独立的内存空间（代码段、数据段、堆、栈），进程间切换开销大。一个进程包含至少一个线程。
- **线程**：CPU 调度执行的基本单位。同一进程内的线程共享进程的内存资源（堆、方法区等），但各自拥有独立的程序计数器和栈。线程间切换开销小，更轻量。
- **区别**：进程独立性强，隔离性好，创建销毁成本高；线程共享内存，通信方便但需处理同步问题，创建销毁成本低。

---

**进程通信（中）**

同一主机上的进程间通信（IPC）方式：
1. **管道**（匿名管道、命名管道）：半双工，数据像水流一样传输。
2. **消息队列**：保存在内核中的消息链表，发送方和接收方通过队列异步通信，克服了管道信号有限的缺点。
3. **共享内存**：多个进程映射同一块物理内存，是最快的 IPC 方式，但需配合信号量同步。
4. **信号量**：主要用于进程间同步，保护共享资源。
5. **信号**：用于通知进程发生了某个事件。
6. **Socket**：可用于不同主机间的进程通信，也可用于本机。

---

**Java 创建线程有几种方式（高）**

1. **继承 Thread 类**：重写 `run()` 方法，调用 `start()` 启动。
2. **实现 Runnable 接口**：实现 `run()` 方法，作为参数传入 `new Thread(runnable).start()`。
3. **实现 Callable 接口**：结合 `FutureTask` 或线程池，`call()` 方法有返回值且可抛异常。
4. **使用线程池**（如 ExecutorService）：通过 `Executors` 工具类或 `ThreadPoolExecutor` 创建，复用线程。

本质都是构建 `Thread` 实例并调用 `start()`，前两种无返回值，Callable 有返回值，线程池为推荐方式。

---

**常见的多线程模型（中）**

1. **线程池模型**：预先创建若干工作线程，任务进入队列，线程循环取任务执行，避免频繁创建销毁线程。
2. **生产者-消费者模型**：通过阻塞队列连接，生产者生产数据放入缓冲区，消费者取走数据，解决速率不匹配问题。
3. **Fork/Join 模型**：将大任务递归拆分成小任务并行执行，最后合并结果，Java 7 引入 ForkJoinPool 实现工作窃取算法。
4. **Actor 模型**：一切皆是 Actor，Actor 间通过消息通信，不共享内存，天然避免死锁（如 Akka）。
5. **Reactor 模型**：事件驱动的 I/O 多路复用模型，单线程或少量线程处理大量连接（Netty、NIO 框架）。

---

**多线程有什么用（中）**

1. **提高 CPU 利用率**：在多核 CPU 上并行执行任务，减少空闲。
2. **提升响应速度**：处理用户请求或 UI 时，将耗时操作放后台线程，避免界面卡顿。
3. **简化程序建模**：某些场景如聊天服务器，一个线程处理一个客户端，逻辑清晰。
4. **提高吞吐量**：Web 服务器通过多线程同时处理多个请求，整体处理能力更强。

---

**什么是多线程中的上下文切换（中）**

CPU 从执行一个线程切换到执行另一个线程时，需要保存当前线程的执行状态（程序计数器、寄存器、栈信息等），并加载新线程之前保存的状态。这个过程称为上下文切换。频繁切换会消耗大量 CPU 时间，降低整体效率。

---

**Thread 类中的 start() 和 run() 方法有什么区别（中）**

- `start()`：启动新线程，新线程会调用 `run()` 方法，调用后立即返回，真正的并发执行。
- `run()`：就是线程要执行的任务，直接调用 `run()` 只是在当前线程执行方法体，不会创建新线程，相当于普通方法调用。

---

**线程间通信方式有哪些？（中）**

Java 中线程间通信机制：
1. **volatile**：保证变量在多线程间的可见性，单变量轻量通信。
2. **synchronized + wait/notify/notifyAll**：基于对象监视器，配合锁实现等待/通知。
3. **Lock + Condition**：`ReentrantLock` 结合 `Condition.await()/signal()`，更灵活的等待通知。
4. **阻塞队列（BlockingQueue）**：生产者-消费者模式，内部已实现线程安全与等待唤醒。
5. **CountDownLatch / CyclicBarrier / Semaphore**：并发工具类，用于协调多线程执行顺序。
6. **管道流（PipedInputStream/PipedOutputStream）**：线程间直接数据传输。
7. **Thread.join()**：让当前线程等待另一个线程执行结束。

## 二、死锁

---

**死锁（中）**

**定义**：两个或多个线程互相持有对方需要的资源，且都在等待对方释放，导致所有线程都无法继续执行的僵持状态。

**四个必要条件**：

1. **互斥条件**：资源不能共享，只能被一个线程占用。
2. **请求与保持条件**：线程已持有一个资源，又在请求其他资源，且不释放当前资源。
3. **不可剥夺条件**：线程获得的资源在未使用完毕前，不能被其他线程强行剥夺。
4. **循环等待条件**：存在一个线程-资源的环形等待链，每个线程都在等待下一个线程占用的资源。

**预防**（破坏四个必要条件之一）：
- 互斥无法破坏（固有属性）。
- 破坏请求与保持：一次性申请所有资源。
- 破坏不可剥夺：若请求资源被占，释放已占资源。
- 破坏循环等待：按顺序申请资源（资源排序）。

**避免**（运行时通过算法判断是否可能进入死锁状态）：
- 银行家算法：系统分配资源前估算是否处于安全状态，不安全则拒绝分配。

**检测与恢复**（允许死锁发生，通过系统检测后采取措施恢复）：
- 检测：使用资源分配图，定期检查是否有环。
- 恢复：剥夺资源、终止进程（回滚）、进程重启等。

## 三、锁基础

---

**常用锁的概念（高）**

锁是并发编程中用于控制多个线程对共享资源访问的机制，核心目标是在保证数据一致性的前提下尽可能提升并发性能。

从不同维度可以对锁进行多种分类：
- **悲观锁 / 乐观锁**：获取资源时是否假定会发生冲突。
- **可重入锁 / 不可重入锁**：同一线程能否重复获取已持有的锁。
- **公平锁 / 非公平锁**：获取锁的顺序是否按请求顺序。
- **共享锁 / 排他锁**：多个线程能否同时持有同一把锁。
- **自旋锁 / 阻塞锁**：获取不到锁时是循环等待还是挂起线程。
- **分段锁**：将数据分段，每段独立加锁，提高并发度。
- **偏向锁 / 轻量级锁 / 重量级锁**：synchronized 的锁升级优化。

---

**Java 中有哪些常用的锁，在什么场景下使用？（高）**

**1. synchronized（内置锁）**
- **概念**：Java 关键字，基于对象监视器（Monitor），自动加锁解锁，支持可重入。
- **场景**：简单同步需求，代码块或方法级别的互斥。适合并发竞争不激烈、锁持有时间短的场景。JDK 6 后性能大幅优化，日常开发优先选用。

**2. ReentrantLock（显式锁）**
- **概念**：`java.util.concurrent.locks` 下的锁实现，需手动 `lock()` 和 `unlock()`，支持可重入。
- **特性**：可尝试非阻塞获取锁（`tryLock`）、可限时等待、可中断获取、支持公平/非公平模式、可绑定多个 Condition。
- **场景**：需要高级功能时使用，如：需要尝试获取锁不阻塞、需要限时等待、需要分离唤醒条件的等待/通知（Condition）。

**3. ReentrantReadWriteLock（读写锁）**
- **概念**：维护一对锁：读锁（共享锁）和写锁（排他锁）。读读不互斥，读写互斥，写写互斥。
- **场景**：读多写少的场景，如缓存访问、配置读取、元数据管理，能显著提升读并发。

**4. StampedLock（Java 8 引入的读写锁增强）**
- **概念**：支持读锁、写锁，还提供乐观读模式。乐观读不加锁，通过版本戳校验数据是否被修改。
- **场景**：在读极多写极少的场景下，乐观读可进一步提升并发，如统计数据读取、热点数据访问。

**5. 悲观锁 / 乐观锁**
- **悲观锁**：假定每次操作都会冲突，先加锁再操作。如 `synchronized`、`ReentrantLock`。
  - **场景**：写多，冲突概率高的场景。
- **乐观锁**：假定不会冲突，操作时不加锁，更新时通过版本号/CAS 校验是否被修改。如数据库版本号、`AtomicInteger`。
  - **场景**：读多写少，冲突概率低的场景，如库存扣减、计数器。

**6. 自旋锁**
- **概念**：获取不到锁时，不立即挂起线程，而是循环尝试一段时间（CAS 循环），避免线程切换开销。synchronized 轻量级锁阶段即采用自旋。
- **场景**：锁持有时间极短的场景，自旋的消耗小于线程挂起恢复的开销。

**7. 分段锁**
- **概念**：将数据分成多个段，每段独立加锁，不同段之间可并发访问。`ConcurrentHashMap`（JDK 7 及以前）采用分段锁实现高并发。
- **场景**：数据结构需要高并发访问，如大型哈希表，JDK 8 后 `ConcurrentHashMap` 改为 CAS + synchronized 实现更细粒度锁。

**8. 偏向锁 / 轻量级锁 / 重量级锁**
- **概念**：synchronized 的锁升级过程。
  - **偏向锁**：无竞争时，锁偏向于第一个获取它的线程，下次该线程再次获取时无需 CAS。
  - **轻量级锁**：有另一个线程竞争时，偏向锁升级为轻量级锁，通过 CAS 和自旋获取。
  - **重量级锁**：自旋失败过多或竞争激烈，膨胀为重量级锁，线程挂起阻塞，由操作系统调度。
- **场景**：JVM 自动优化，开发者无感知。偏向锁适合总是单线程访问同步块的场景。

**9. 公平锁 / 非公平锁**
- **公平锁**：线程按请求顺序获取锁，`new ReentrantLock(true)`。
  - **场景**：对公平性要求高的场景，避免线程饥饿。
- **非公平锁**：允许插队，吞吐量更高，synchronized 和 `ReentrantLock` 默认都是非公平。
  - **场景**：大多数场景，追求更高性能。

**10. Semaphore（信号量）**
- **概念**：持有若干许可，线程调用 `acquire()` 获取许可，`release()` 释放。可限制同时访问资源的线程数。
- **场景**：流量控制、连接池限制、限流等。如数据库连接数限制。

**11. CountDownLatch / CyclicBarrier**
- **CountDownLatch**：一个线程等待其他多个线程完成任务后继续执行。
  - **场景**：主线程等待多个子任务全部完成再汇总结果。
- **CyclicBarrier**：一组线程互相等待，达到共同点后一起继续执行。
  - **场景**：多线程分片计算，等待所有线程完成同一阶段后再进入下一阶段。

**12. Phaser（阶段器）**
- **概念**：可重用的同步屏障，功能比 CyclicBarrier 更灵活，支持动态增减参与者。
- **场景**：分阶段任务协调，如并行计算流水线各阶段同步。

## 四、synchronized

---

**说一说自己对于 synchronized 关键字的了解（高）**

`synchronized` 是 Java 内置的互斥同步锁，用于保证多线程环境下共享变量的可见性、原子性和有序性。主要特性：
- **互斥性**：同一时刻只有一个线程能执行被 synchronized 修饰的代码块或方法。
- **可重入性**：同一线程的外层函数获得锁后，内层函数可直接再次获取该锁，不会自我死锁。
- **内置锁**：基于 JVM 内置的对象监视器（Monitor）实现，无需显式加锁解锁，代码块结束或异常时自动释放锁。
- **锁升级优化**（JDK 6+）：经历了偏向锁→轻量级锁→重量级锁的逐步膨胀过程，在无竞争或轻度竞争下大幅提升性能。
- **内存语义**：加锁时清空工作内存，从主存读取；解锁时把工作内存的变量写回主存，保证可见性（遵循 happens-before 原则）。

---

**怎么使用 synchronized 关键字（高）**

1. **修饰实例方法**（普通同步方法）
   ```java
   public synchronized void method() { ... }
   ```
   锁对象为当前实例对象 `this`。

2. **修饰静态方法**
   ```java
   public static synchronized void method() { ... }
   ```
   锁对象为当前类的 `Class` 对象。

3. **修饰代码块**
   ```java
   synchronized(obj) { ... }
   ```
   锁对象为括号内指定的对象，可灵活选择锁粒度。

- 对于实例方法，作用于当前实例；不同实例调用互不干扰。
- 对于静态方法，作用于整个类，所有实例共享一把锁。
- 使用时应尽量将同步范围缩小到必要的临界区，以提高并发性能。

---

**synchronized 原理（高）**

基于对象监视器（Monitor）实现，依赖 JVM 指令和操作系统互斥量。

- **字节码层面**：
  - 同步代码块：使用 `monitorenter` 和 `monitorexit` 指令。`monitorenter` 尝试获取对象的监视器锁，计数器从0加1；`monitorexit` 计数器减1，归零则释放锁。异常表也会自动插入 `monitorexit` 保证解锁。
  - 同步方法：方法访问标志设置 `ACC_SYNCHRONIZED`，表示需要隐式获取监视器锁，方法执行期间持有，返回或异常时释放。

- **对象头与 Monitor**：
  每个 Java 对象头中都有 Mark Word，存储了锁状态信息、线程 ID、指向 Monitor 对象的指针等。JVM 为每个对象关联一个 Monitor 对象（C++ 的 `ObjectMonitor`），内部包含 `_owner`（持有线程）、`_EntryList`（阻塞等待线程）、`_WaitSet`（wait 线程）等。

- **重量级锁流程**：
  当锁膨胀为重量级锁时，线程通过操作系统互斥量（mutex）实现阻塞和唤醒，未获取到锁的线程进入 `EntryList` 阻塞，释放锁时唤醒。

---

**synchronized 可重入如何实现（高）**

`synchronized` 的可重入性由 Monitor 内部的计数器实现：
- 每个 Monitor 维护一个 **重入计数器**（`_recursions`）和 **持有者线程**（`_owner`）。
- 当线程进入同步块时：
  - 若 `_owner` 为 null，则该线程成为 owner，计数器置为 1。
  - 若 `_owner` 是当前线程，则计数器加 1（重入）。
- 退出同步块（`monitorexit`）时，计数器减 1；当计数器归零时，清除 `_owner`，释放锁。
- 这样就允许同一线程多次获取同一把锁而不会死锁。

---

**JDK1.6 之后的 synchronized 底层做了哪些优化？（高）**

JDK 6 引入了大量锁优化，大幅提升了 synchronized 在无竞争或轻度竞争下的性能：

1. **偏向锁（Biased Locking）**
   - 当锁总是被同一线程获取时，Mark Word 记录该线程 ID，该线程再次进入只需比对 ID 即可，无需 CAS 操作。
   - 一旦有其他线程竞争，偏向锁撤销，升级为轻量级锁。

2. **轻量级锁（Lightweight Locking）**
   - 多个线程交替执行同步块（无实际竞争），通过 CAS 尝试将对象头的 Mark Word 替换为指向当前线程栈中锁记录（Lock Record）的指针。
   - 若成功则获取轻量级锁；若失败且存在竞争，则膨胀为重量级锁。

3. **自旋锁（Spin Locking）**
   - 当轻量级锁获取失败，线程不立即挂起，而是做若干次空循环（自旋）等待锁释放，避免线程切换开销。
   - 自旋次数可自适应（Adaptive Spinning），由 JVM 根据之前的自旋成功率动态调整。

4. **锁粗化（Lock Coarsening）**
   - 若一系列连续操作对同一对象反复加锁解锁（如循环内加锁），JIT 会将锁的范围扩展到整个操作序列外部，减少锁获取次数。

5. **锁消除（Lock Elimination）**
   - JIT 在编译时通过逃逸分析判断同步代码是否可能被多线程访问。如果对象不会逃逸到线程外，则去掉同步锁，消除无意义的加锁开销。

这些优化使 synchronized 在大部分场景下与显式锁性能相当，甚至在简单场景更优。

## 五、Lock 与 CAS

---

**Lock 和 synchronized 异同？（高）**

| 对比项             | synchronized                                                 | Lock（如 ReentrantLock）                                  |
| ------------------ | ------------------------------------------------------------ | --------------------------------------------------------- |
| **实现方式**       | JVM 内置，关键字                                             | JDK 代码实现，`java.util.concurrent.locks` 接口           |
| **锁的获取与释放** | 自动加锁和解锁，退出同步块或异常时自动释放                   | 必须手动 `lock()` 和 `unlock()`，通常在 finally 块中释放  |
| **可中断性**       | 不可中断，等待锁的线程会一直阻塞                             | 可中断，`lockInterruptibly()` 可在等待锁时响应中断        |
| **超时获取**       | 不支持，只能无限期等待                                       | 支持，`tryLock(time, unit)` 可指定超时时间                |
| **公平性**         | 非公平锁                                                     | 支持公平/非公平模式，`new ReentrantLock(true)` 构造公平锁 |
| **条件变量**       | 使用 `wait/notify/notifyAll` 与锁对象绑定，只能有一个等待队列 | 可创建多个 `Condition`，实现更精确的等待/通知控制         |
| **尝试非阻塞获取** | 不支持                                                       | 支持 `tryLock()`，尝试获取锁，失败立即返回                |
| **性能**           | JDK 6 后经过大量优化，性能接近 ReentrantLock                 | 在竞争激烈或需要高级特性时更灵活                          |
| **适用场景**       | 简单的同步需求，代码简洁                                     | 需要可中断、超时、公平锁、多条件等高级功能的场景          |

两者都是可重入的排它锁，都遵守 happens-before 原则，保证可见性和原子性。优先使用 synchronized，需要高级特性时使用 Lock。

---

**CAS 了解吗（高）**

CAS（Compare And Swap，比较并交换）是一种无锁（lock-free）的原子操作，广泛应用于 Java 并发编程中。它由底层硬件指令提供支持，是乐观锁的核心实现手段。

- Java 中通过 `sun.misc.Unsafe` 类提供的 `compareAndSwapXXX` 方法实现，这些方法被包装成 `java.util.concurrent.atomic` 包下的原子类（如 `AtomicInteger`, `AtomicReference` 等）。
- CAS 涉及三个操作数：内存位置 V、预期原值 A、新值 B。
- 当且仅当 V 的值等于 A 时，处理器才会将 V 的值更新为 B，否则不执行更新。无论是否成功，都会返回 V 的旧值。
- 整个过程由硬件保证原子性（通过总线锁定或缓存锁定），一个 CPU 指令完成。

---

**CAS 原理（高）**

**1. 底层实现**
现代 CPU 提供专门的原子指令来支持 CAS 操作：
- x86 架构：`CMPXCHG` 指令。
- ARM 架构：`LDREX/STREX` 指令对。

Java 的 `Unsafe` 类通过 JNI 调用这些本地方法来执行 CAS，编译器会将其转化为对应的 CPU 原子指令。

**2. 执行流程**
```
CAS(V, A, B):
    if (V == A) {
        V = B;
        return true;  // 更新成功
    } else {
        return false; // 更新失败
    }
```
- 读取内存位置 V 的当前值。
- 与期望值 A 比较。
- 若相等，将新值 B 写入 V；若不相等，说明被其他线程修改过，操作失败。
- 整个过程在硬件层面是原子的，中间不会被中断。

**3. Java 中的应用**
- 原子类（`AtomicInteger`）的 `incrementAndGet()` 内部使用 CAS 循环自旋直至成功。
- 无锁数据结构（如 `ConcurrentLinkedQueue`）。
- `synchronized` 轻量级锁的获取也是通过 CAS 来修改对象头中的 Mark Word。
- `AQS`（AbstractQueuedSynchronizer）框架中的状态变更使用 CAS。

---

**乐观锁存在哪些问题？（高）**

乐观锁假设冲突少，不加锁直接操作，提交时通过版本号或 CAS 检测冲突。但它有以下问题：

**1. 循环自旋的开销**
CAS 失败时会通过循环不断重试，如果长时间不成功，会给 CPU 带来非常大的执行开销。尤其在并发竞争激烈的场景下，CAS 自旋可能退化为忙等，影响性能。

**2. 只能保证一个共享变量的原子性**
CAS 只能对单个内存位置进行操作。当需要对多个共享变量进行原子更新时，无法直接使用 CAS（除非用 `AtomicReference` 将多个变量封装到一个对象中，但这样也增加了复杂性）。

**3. ABA 问题**
见下文详述，CAS 仅比较值，无法感知值的变化过程。一个值从 A 变成 B 又变回 A，CAS 检查时会误认为没有被修改过，可能引发业务逻辑错误。

**4. 与数据库乐观锁配合的写入压力**
如果数据库层面实现乐观锁（版本号），在高并发下可能导致大量更新冲突和重试，增加数据库压力。

---

**什么是 ABA 问题？ABA 问题怎么解决？（高）**

**1. 定义**
ABA 问题是指在 CAS 操作中，一个共享变量的值原来是 A，被其他线程修改为 B，之后又修改回 A。此时当前线程执行 CAS 时发现值仍然是 A，误以为它没有被改变过，从而 CAS 成功更新。但实际上该变量的状态已经经历了 A→B→A 的变化，可能对依赖状态变化逻辑的业务造成影响。

**典型例子**
- 链表头节点操作：线程1 读取栈顶节点 A，准备 CAS 将栈顶设为 B。线程2 在此期间把 A 弹出，然后压入 C，最后又把 A 压回。栈顶又变成 A，但链表结构已变。线程1 的 CAS 可能成功，但 B 的 next 指针实际上已经失效，造成链表损坏。

**2. 解决方案：版本号/时间戳**
核心思想是为变量增加一个版本号或时间戳，不仅仅比较值，还比较版本是否发生变化。

**Java 中的解决工具**
- **`AtomicStampedReference`**：使用一个整数"戳记"（stamp）作为版本号，每次更新都修改 stamp。CAS 时同时比较引用值和 stamp 值，两者都相等才更新。适用于需要精确记录修改次数的场景。
- **`AtomicMarkableReference`**：使用一个布尔标记，不记录修改次数，只关心"是否被修改过"，适用于简单的"可用/不可用"等二元状态场景。

**数据库中的解决**
- 在数据库表中使用 version 字段（整数或时间戳），每次更新时 `update ... set version = version + 1 where id = ? and version = ?`，通过比较版本号防止 ABA 问题。

---

## 六、AQS

---

**AQS 是什么？AQS 的原理是什么？（高）**

**定义**
AQS（AbstractQueuedSynchronizer，抽象队列同步器）是 Java 并发包 `java.util.concurrent.locks` 的核心框架，它是一个用于构建锁和其他同步组件（如 `ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock` 等）的基础类。它使用一个 `volatile int` 成员变量表示同步状态，并通过一个内置的 FIFO 双向队列（CLH 变体）来管理等待线程。

**核心原理**

1. **同步状态 `state`**
   - 一个 `volatile int` 变量，表示同步状态（如锁被重入的次数、信号量的剩余许可等）。
   - 提供 `getState()`、`setState(int)`、`compareAndSetState(int expect, int update)` 三个方法操作状态，其中后者基于 CAS 保证原子修改。

2. **CLH 队列（等待队列）**
   - 是一个虚拟的双向队列（基于 Node 节点），节点中保存了等待线程的引用、等待状态（`waitStatus`）、前驱和后继节点指针。
   - 当线程获取同步状态失败时，会被包装成 `Node` 节点，通过 CAS 操作安全地插入队列尾部，然后通过 `LockSupport.park()` 挂起线程。
   - 当同步状态释放时，前驱节点会唤醒后继节点（`LockSupport.unpark()`），被唤醒的线程重新尝试获取同步状态。

3. **模板方法模式**
   - AQS 采用模板方法设计模式，对外提供统一的获取和释放锁的骨架逻辑，而将"如何判断是否可以获得同步状态"、"如何定义状态值"交给子类实现。
   - 子类需要重写的方法：`tryAcquire`（独占获取）、`tryRelease`（独占释放）、`tryAcquireShared`（共享获取）、`tryReleaseShared`（共享释放）、`isHeldExclusively`（是否独占）。

4. **独占与共享模式**
   - AQS 同时支持独占模式（Exclusive）和共享模式（Shared），同一个 AQS 实例通常只使用其中一种模式（`ReentrantReadWriteLock` 内部使用两个 AQS，分别实现读锁和写锁）。

---

**讲一下 AQS 的独占和共享模式（中）**

**1. 独占模式（Exclusive）**
- **含义**：同一时刻只允许一个线程获取同步状态，其他线程必须排队等待。
- **获取流程**（以 `acquire` 为例）：
  1. 调用子类实现的 `tryAcquire(arg)` 尝试获取同步状态。
  2. 若获取失败，线程被包装成 `Node.EXCLUSIVE` 节点，通过 CAS 加入等待队列尾部。
  3. 进入队列后，线程不断检查自己的前驱节点是否为头节点（head），若是则再次尝试 `tryAcquire`。
  4. 若仍失败，判断是否应挂起（`shouldParkAfterFailedAcquire`），若需要则调用 `LockSupport.park()` 挂起线程。
- **释放流程**（`release`）：
  1. 调用子类实现的 `tryRelease(arg)` 释放同步状态。
  2. 若释放成功，唤醒头节点的后继节点（`unparkSuccessor`），使其重新竞争锁。
- **典型应用**：`ReentrantLock` 的 `NonfairSync` 和 `FairSync`。

**2. 共享模式（Shared）**
- **含义**：同一时刻允许多个线程同时获取同步状态，共享访问资源。
- **获取流程**（以 `acquireShared` 为例）：
  1. 调用子类实现的 `tryAcquireShared(arg)`，返回值 >=0 表示成功获取，且返回值表示剩余可用资源数；<0 表示获取失败。
  2. 获取失败则线程被包装成 `Node.SHARED` 节点，加入等待队列尾部。
  3. 进入队列后，同样检查前驱是否为 head，若是则尝试 `tryAcquireShared`。
  4. 获取成功后，若仍有剩余资源，会通过 `setHeadAndPropagate` 传播唤醒，即头节点获取成功后，会连续唤醒后面连续的共享节点，让更多线程并发获取，实现"共享"。
- **释放流程**（`releaseShared`）：
  1. 调用子类实现的 `tryReleaseShared(arg)`。
  2. 若成功，同样通过 `doReleaseShared` 唤醒后继节点，可能引发连锁唤醒。
- **典型应用**：`Semaphore`（信号量）、`CountDownLatch`、`ReentrantReadWriteLock` 的读锁。

**3. 二者关键区别**
| 特点           | 独占模式                   | 共享模式                                     |
| -------------- | -------------------------- | -------------------------------------------- |
| 同时持有线程数 | 1个                        | 多个                                         |
| Node 标记      | `Node.EXCLUSIVE`           | `Node.SHARED`                                |
| 获取方法       | `tryAcquire` / `acquire`   | `tryAcquireShared` / `acquireShared`         |
| 释放后行为     | 仅唤醒队列中第一个等待节点 | 唤醒后继节点后可能连续传播，唤醒一串共享节点 |
| 典型实现       | `ReentrantLock`            | `Semaphore`、`CountDownLatch`                |

---

## 七、ReentrantLock

---

**ReentrantLock 底层原理（高）**

`ReentrantLock` 的底层基于 **AQS（AbstractQueuedSynchronizer）** 实现，内部使用一个继承自 AQS 的同步器 `Sync`，并有两个子类 `NonfairSync` 和 `FairSync` 分别对应非公平锁和公平锁。

**核心结构**
- AQS 中维护一个 `volatile int state`，表示锁的同步状态（对于 ReentrantLock，0 表示未被持有，>0 表示锁被持有的重入次数）。
- 通过内置的 FIFO 双向队列（CLH 变体）管理等待线程，每个等待线程被封装成一个 `Node` 节点。

**加锁流程（以非公平锁为例）**
1. **快速尝试 CAS**：调用 `lock()` 时，先直接通过 CAS 尝试将 state 从 0 改为 1。若成功，则将 `exclusiveOwnerThread` 设为当前线程，加锁成功。
2. **正式获取**：若 CAS 失败，调用 `acquire(1)`（AQS 模板方法）。
   - 首先调用 `tryAcquire(arg)`，内部会再次检测 state：
     - 若 state == 0，尝试 CAS 抢占（非公平锁允许插队）。
     - 若 state != 0 且持有线程是当前线程，则 `state += arg`（可重入），返回 true。
     - 否则返回 false。
   - 若 `tryAcquire` 失败，则线程被包装成 `Node.EXCLUSIVE` 节点，通过 CAS 自旋加入等待队列尾部。
   - 加入队列后，通过 `acquireQueued` 方法自旋或阻塞，不断尝试获取锁。前驱为头节点时尝试 `tryAcquire`，失败则通过 `LockSupport.park()` 挂起，等待唤醒。

**解锁流程**
- 调用 `release(1)`，内部执行 `tryRelease(arg)`：
  - 计算 `state -= arg`，若 `state == 0`，将 `exclusiveOwnerThread` 置为 null，返回 true 表示锁完全释放。
  - 若 `state > 0`（重入尚未完全释放），返回 false。
- 当锁完全释放后，唤醒等待队列中的头节点的后继节点（`unparkSuccessor`），使其重新竞争锁。

**可重入实现**

可重入性指的是同一个线程可以多次获取同一把锁而不会被自己阻塞。`ReentrantLock` 通过 AQS 的 `state` 变量和一个 `exclusiveOwnerThread` 字段配合实现：

1. **加锁时可重入**（`tryAcquire` 中）：
   - 读取当前 `state`。
   - 若 `state != 0`，说明锁已被某线程持有，检查 `exclusiveOwnerThread` 是否是当前线程。
   - 如果是同一线程，则 `state = state + acquires`（通常加 1），表示重入次数增加，获取成功，返回 true。
   - 如果不是当前线程，则获取失败，进入排队。

2. **解锁时可重入**（`tryRelease` 中）：
   - 计算 `state = state - releases`。
   - 判断 `state` 是否为 0。
   - 若为 0，说明已经完全解锁，将 `exclusiveOwnerThread` 置为 null，锁被彻底释放，可以唤醒后继节点。
   - 若不为 0，说明还有重入次数未释放，返回 false，锁依然被当前线程持有。

这样，同一个线程无论调用多少次 `lock()`，只要对应调用相同次数的 `unlock()`，锁就能正确释放，既保证了重入，也防止了死锁。

**公平锁与非公平锁差异**
- **非公平锁**：`tryAcquire` 中若发现 state == 0，会直接 CAS 尝试获取，不需要判断队列中是否有等待更久的线程。
- **公平锁**：`tryAcquire` 中会先调用 `hasQueuedPredecessors()` 判断等待队列中是否有前驱节点，若有则必须排队，不能插队。

## 八、JMM（Java 内存模型）

---

**什么是 JMM（中）**

JMM（Java Memory Model，Java 内存模型）是 Java 虚拟机规范中定义的一套**并发编程内存访问规则**，它抽象描述了程序中变量的访问方式以及线程间的交互机制。

核心内容：
- **主内存与工作内存**：所有变量存储在主内存（所有线程共享），每个线程有自己私有的工作内存（高速缓存或寄存器），工作内存保存了该线程使用的变量的主内存副本。
- **8 种原子操作**：定义了变量在工作内存和主内存之间的具体交互流程，包括 lock、unlock、read、load、use、assign、store、write 等操作。
- 线程对变量的所有操作（读/写）必须在工作内存中进行，不能直接读写主内存。变量在工作内存修改后，在特定时机同步回主内存。
- 定义了**可见性、有序性、原子性**的语义保障，以及 `volatile`、`synchronized` 等关键字的内存语义。

JMM 屏蔽了不同硬件/操作系统内存访问方式的差异，确保 Java 程序在各种平台下具有一致的并发行为。

---

**为什么需要 JMM？（中）**

1. **屏蔽底层硬件差异**
   不同 CPU 架构的缓存一致性协议、指令重排序策略各不相同，JMM 提供了统一的内存抽象，使得 Java 编写一次，到处运行。

2. **解决线程安全问题**
   多线程下会出现原子性、可见性、有序性问题。JMM 通过规定内存交互顺序、提供 `volatile`、`synchronized` 等机制，为开发者提供了解决这些问题的语义保障。

3. **给编译器/处理器优化划定边界**
   为了提高性能，编译器和处理器会进行指令重排序，JMM 通过 happens-before 等规则约束哪些重排序是禁止的，保证在正确使用同步的前提下，程序结果与预期一致。

4. **规范安全发布和初始化**
   JMM 规定了对 `final` 域、静态初始化等的特殊处理，确保对象被正确构造并安全地发布给其他线程。

---

**线程安全三个问题的保障方案（中）**

线程安全问题主要由三个根源导致：**原子性、可见性、有序性**，Java 提供了对应的保障方案。

| 问题       | 描述                                                     | 保障方案                                                     |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| **原子性** | 一个或多个操作不可分割，要么全部执行成功，要么全部不执行 | `synchronized`、`Lock`（`ReentrantLock`）、`java.util.concurrent.atomic` 包下的原子类（如 `AtomicInteger`） |
| **可见性** | 一个线程对共享变量的修改，其他线程能立即看到             | `volatile` 关键字、`synchronized`、`Lock`、`final` 字段（正确构造后） |
| **有序性** | 程序执行的顺序按照代码的先后顺序，不发生指令重排序       | `volatile`（禁止重排序）、`synchronized`、`Lock`（临界区内禁止与外部指令重排）、`happens-before` 规则 |

**详细说明：**
- `synchronized` 和 `Lock` 同时保证了原子性、可见性和有序性。
- `volatile` 保证可见性和有序性（禁止指令重排），但不保证原子性。
- 原子类通过 CAS 循环保证原子性和可见性。

---

**happens-before（低）**

happens-before 是 JMM 定义的**部分偏序关系**，用于判断两个操作之间是否存在先后顺序以及内存可见性保障。如果操作 A happens-before 操作 B，意味着 A 的执行结果对 B 可见，且 A 的执行顺序在 B 之前。

**核心规则：**
1. **程序次序规则**：同一个线程内，代码书写在前面的操作 happens-before 书写在后面的操作。
2. **监视器锁规则**：对一个锁的解锁（unlock）happens-before 后续对这个锁的加锁（lock）。
3. **volatile 变量规则**：对一个 volatile 域的写 happens-before 后续对这个 volatile 域的读。
4. **线程启动规则**：线程 A 的 `Thread.start()` 调用 happens-before 新线程 B 中的任何操作。
5. **线程终止规则**：线程 A 中的所有操作 happens-before 线程 B 的 `A.join()` 成功返回。
6. **中断规则**：对线程 `interrupt()` 方法的调用 happens-before 被中断线程检测到中断事件。
7. **传递性**：如果 A happens-before B，B happens-before C，则 A happens-before C。

这些规则为编写线程安全程序提供了可见性保证基础，只要满足 happens-before 关系，就无需额外的同步措施来保证内存可见性。

---

## 九、volatile

---

**Volatile 三大特性（高）**

`volatile` 是 Java 中轻量级的同步机制，它主要有以下三大特性：

1. **保证可见性**
   - 当一个线程修改了 `volatile` 变量的值，新值会立即被刷新到主内存中，其他线程读取该变量时会强制从主内存中读取，从而保证所有线程看到的值是一致的。
   - 实现原理：通过 CPU 的缓存一致性协议（如 MESI）和内存屏障，写 `volatile` 时会强制将工作内存的修改刷新到主内存，读 `volatile` 时会强制从主内存加载新值。

2. **禁止指令重排序**
   - JVM 和 CPU 为了提高性能会对指令进行重排序，但 `volatile` 通过插入**内存屏障**来禁止特定情况下的重排序，确保在其前后的指令不会被乱序执行到屏障的另一侧。
   - 这保证了 `volatile` 变量的写操作在读操作之前发生（单线程视角下的语义）。

3. **不保证原子性**
   - `volatile` 修饰的变量，其读写操作本身是原子的（如 32 位变量的读写），但像 `i++` 这样的复合操作（读-改-写）仍然不是原子性的，多线程并发执行仍会导致数据不一致。这是它与 `synchronized` 的一个重要区别。

---

**Volatile 和 synchronized 的区别（高）**

| 对比项           | volatile                       | synchronized                               |
| ---------------- | ------------------------------ | ------------------------------------------ |
| **性质**         | 轻量级的变量修饰符             | 重量级锁，可修饰方法或代码块               |
| **保证可见性**   | 是                             | 是                                         |
| **保证原子性**   | 否（复合操作如 `i++` 不安全）  | 是（临界区内代码原子执行）                 |
| **禁止指令重排** | 是（针对该变量前后的操作）     | 是（临界区内禁止与外部重排）               |
| **线程阻塞**     | 不会导致线程阻塞               | 未获取锁的线程会阻塞并被操作系统挂起       |
| **性能开销**     | 很小，仅涉及内存屏障           | 较大，涉及线程上下文切换和系统调用         |
| **适用场景**     | 状态标记、双重检查锁中的单例等 | 需要原子性、复杂同步逻辑、多条件等待的场景 |

`volatile` 是 `synchronized` 的轻量替代，但只能解决部分可见性和有序性问题，无法替代需要原子性保障的场景。

---

**为什么 volatile 不能保证线程安全？（高）**

线程安全要求同时满足**可见性、原子性、有序性**。`volatile` 满足了可见性和有序性（禁止指令重排），但缺少原子性支持，因此无法保证线程安全。

以 `num++` 为例，它是一个"读-改-写"复合操作：
1. 读取 `num` 的值（此时即使是最新值，多个线程可能同时读到相同的值）。
2. 计算值加 1。
3. 将结果写回主内存。

多个线程可能交替执行这三个步骤，导致某些增量丢失。因为 `volatile` 不能将这三步合成为一个不可分割的原子操作，所以即使变量可见，结果依然可能出错。这就需要用 `synchronized`、`Lock` 或 `AtomicInteger` 来提供原子性。

---

**如果不使用 lock 和 synchronized，怎么保证 num++ 的原子性？（高）**

可以使用 **原子类（Atomic 类）**，它们在 `java.util.concurrent.atomic` 包下，利用 CAS（Compare And Swap）机制实现无锁原子操作。

例如，使用 `AtomicInteger`：
```java
AtomicInteger num = new AtomicInteger(0);
num.incrementAndGet();  // 相当于 num++，保证原子性
```
- `incrementAndGet()` 内部通过 `Unsafe` 类的 `compareAndSwapInt` 方法进行 CAS 循环：读取当前值 → 加 1 → 比较并交换，如果交换失败（说明值被其他线程修改过），则重新读取并重试，直到成功为止。
- CAS 由 CPU 硬件提供原子指令支持，无锁、非阻塞，性能优于 `synchronized`，但遇到高竞争时可能自旋严重。
- 除了 `AtomicInteger`，还有 `AtomicLong`、`AtomicReference` 等，以及针对字段的 `AtomicIntegerFieldUpdater`，都可以用来保证单一变量的原子操作。

---

**volatile 禁止指令重排序的原理是什么（中）**

`volatile` 禁止指令重排序是通过**内存屏障（Memory Barrier）** 实现的。内存屏障是一类 CPU 指令，用于限制编译器及 CPU 对指令的重排序，并强制内存可见性。

JMM 为 `volatile` 变量定义了特定的屏障插入策略：

- **在 volatile 写之前，插入 StoreStore 屏障**
  禁止 volatile 写与前面任意写操作重排序。
- **在 volatile 写之后，插入 StoreLoad 屏障**
  禁止 volatile 写与后面可能出现的读/写操作重排序，同时强制刷新写缓冲，使得 volatile 写的结果对其他处理器可见。这是最"重"的屏障。
- **在 volatile 读之后，插入 LoadLoad 屏障**
  禁止 volatile 读与后面普通读操作重排序。
- **在 volatile 读之后，插入 LoadStore 屏障**
  禁止 volatile 读与后面写操作重排序。

这些屏障的插入点在 JIT 编译时由 JVM 根据 JMM 规则确定，最终转化为特定 CPU 架构的屏障指令（如 x86 的 `lock` 前缀指令或 `mfence/lfence/sfence`），从硬件层面阻止指令乱序执行，保证 `volatile` 变量读写的顺序语义。

## 十、线程池

---

**ThreadPoolExecutor 构造函数（高）**

`ThreadPoolExecutor` 最完整的构造函数有 7 个参数：

```java
ThreadPoolExecutor(int corePoolSize,
                   int maximumPoolSize,
                   long keepAliveTime,
                   TimeUnit unit,
                   BlockingQueue<Runnable> workQueue,
                   ThreadFactory threadFactory,
                   RejectedExecutionHandler handler)
```

- **corePoolSize**：核心线程数，即使空闲也保留在线程池中（除非设置 `allowCoreThreadTimeOut`）。
- **maximumPoolSize**：线程池最大允许的线程数。
- **keepAliveTime**：当线程数超过核心数时，多余空闲线程在终止前等待新任务的最长时间。
- **unit**：`keepAliveTime` 的时间单位。
- **workQueue**：存放等待执行任务的阻塞队列。
- **threadFactory**：创建新线程的工厂，可自定义名称、优先级、守护状态等。
- **handler**：当任务队列满且线程数达到 `maximumPoolSize` 时的拒绝策略。

---

**提交一个新任务到线程池时，具体的执行流程 / 线程池的工作流程（高）**

1. 判断核心线程数是否已满：若当前线程数 < `corePoolSize`，则直接创建新线程执行任务（即使存在空闲核心线程）。
2. 若核心线程数已满，尝试将任务放入 `workQueue` 等待。
3. 若队列已满，判断当前线程数是否 < `maximumPoolSize`，若是则创建非核心线程执行任务。
4. 若队列已满且线程数已达 `maximumPoolSize`，则执行拒绝策略（`RejectedExecutionHandler`）。

---

**线程池线程数如何设置？（高）**

根据任务类型不同，选择不同估算方式：
- **CPU 密集型**：线程数 = CPU 核心数 + 1。尽量减少上下文切换，CPU 利用率最高。
- **I/O 密集型**：线程数 = CPU 核心数 × (1 + 平均等待时间/平均计算时间) 或直接使用 **核心数 × 2**。由于大量线程阻塞等待 I/O，可设置较多线程提高并发。
- **混合型**：可将任务拆分，分别使用不同的线程池；或通过压测调整到最佳值。
- 实际经验：最好结合压测和动态监控最终确定，`Runtime.getRuntime().availableProcessors()` 获取核心数。

---

**线程池中 submit() 和 execute() 方法有什么区别（中）**

| 方法        | 来源                   | 参数                            | 返回值        | 异常处理                                                     |
| ----------- | ---------------------- | ------------------------------- | ------------- | ------------------------------------------------------------ |
| `execute()` | `Executor` 接口        | 只接受 `Runnable`               | 无返回值      | 任务执行中未捕获异常会抛出到线程，可由 `UncaughtExceptionHandler` 处理 |
| `submit()`  | `ExecutorService` 接口 | 可接受 `Runnable` 或 `Callable` | 返回 `Future` | 异常被捕获封装在 `Future` 中，调用 `get()` 时会抛出 `ExecutionException` |

- `submit()` 能获取任务执行结果和异常，灵活性更高；`execute()` 更基础，不关心结果时可用。

---

**Executors 中的常用线程池（高）**

`Executors` 提供以下快捷工厂方法：
1. **newFixedThreadPool(n)**：固定大小线程池，核心线程数=最大线程数=n，无界队列（LinkedBlockingQueue），线程空闲不会回收。
2. **newSingleThreadExecutor()**：单线程线程池，所有任务串行执行，适合顺序处理场景。
3. **newCachedThreadPool()**：核心线程数为0，最大线程数为 `Integer.MAX_VALUE`，使用同步移交队列 `SynchronousQueue`，空闲线程60秒回收，适合大量短任务。
4. **newScheduledThreadPool(n)**：支持定时及周期性任务执行，底层使用 `DelayedWorkQueue`。
5. **newWorkStealingPool()**（Java 8）：基于 `ForkJoinPool`，工作窃取算法，并行级别默认为 CPU 核心数。

---

**Executors 创建线程池会存在什么问题（高）**

《阿里巴巴 Java 开发手册》强制要求不要使用 `Executors` 创建线程池，原因：
- **newFixedThreadPool / newSingleThreadExecutor**：使用无界 `LinkedBlockingQueue`，队列可能无限堆积，导致 OOM。
- **newCachedThreadPool / newScheduledThreadPool**：允许创建的线程数为 `Integer.MAX_VALUE`，高并发下可能创建巨量线程，导致 CPU 耗尽或 OOM。
- **最佳实践**：直接使用 `ThreadPoolExecutor` 构造函数，明确指定队列容量和线程数上限，配合合理的拒绝策略，资源更可控。

---

**线程池的拒绝策略（中）**

当任务队列满且线程数达到最大线程数时，触发拒绝策略。JDK 内置四种：
1. **AbortPolicy（默认）**：抛出 `RejectedExecutionException` 异常，通知调用者。
2. **CallerRunsPolicy**：由提交任务的调用线程直接执行该任务，减缓任务提交速度。
3. **DiscardPolicy**：直接丢弃新任务，不抛异常，不通知。
4. **DiscardOldestPolicy**：丢弃队列头部（等待最久）的任务，然后重新提交当前任务。
5. 也可自定义实现 `RejectedExecutionHandler` 接口，比如记录日志、持久化到数据库、发送告警等。

## 十一、ThreadLocal

---

**什么是 ThreadLocal / ThreadLocal 有什么用？（高）**

`ThreadLocal` 是 Java 提供的**线程本地存储**机制。它为每个使用该变量的线程都创建了一个独立的副本，线程只能访问和修改自己的那份副本，从而实现了线程间的数据隔离，避免了变量在多线程环境下的共享冲突。

主要用途：
- **线程封闭**：将某个对象封闭在线程内部，不与其他线程共享，自动保证线程安全（如 SimpleDateFormat 不是线程安全，使用 ThreadLocal 可让每个线程持有自己的实例）。
- **上下文传递**：在同一个线程的多个方法、多个模块之间传递全局信息，而不必通过方法参数逐层传递。典型例子：Web 开发中，在过滤器中把当前请求的用户信息、Session 存入 ThreadLocal，后面的 Service、DAO 层可以直接获取。
- **数据库连接管理**：Spring 的事务管理中用 ThreadLocal 存放当前线程的数据库连接，确保同一事务中 DAO 操作使用同一个连接。

---

**ThreadLocal 原理（高）**

ThreadLocal 的核心机制是每个线程 `Thread` 对象内部都有一个 `ThreadLocalMap`，键是 `ThreadLocal` 实例的弱引用，值是该线程对应的变量副本。

**数据结构**
- `Thread` 类有一个 `threadLocals` 字段（类型为 `ThreadLocal.ThreadLocalMap`），用于存储该线程所有 ThreadLocal 变量。
- `ThreadLocalMap` 是一个自定义的哈希表，内部使用 `Entry[]` 数组。`Entry` 继承自 `WeakReference<ThreadLocal<?>>`，以 ThreadLocal 对象为键（弱引用），变量副本为值。

**存取流程**
- **set(T value)**：获取当前线程的 `ThreadLocalMap`，若不存在则创建；然后以当前 `ThreadLocal` 实例为键，存储值。
- **get()**：获取当前线程的 `ThreadLocalMap`，以当前 `ThreadLocal` 实例查找对应的值；若未找到，调用 `initialValue()` 初始化默认值。
- **remove()**：从当前线程的 `ThreadLocalMap` 中删除对应的 Entry。

**ThreadLocal 哈希冲突解决**
- 不同于 `HashMap` 的链表法，`ThreadLocalMap` 使用**线性探测法**（开放地址法）解决冲突。当插入位置被占用时，会依次往后查找下一个可用槽位。

**关键点**
- 变量副本实际上是保存在线程 `Thread` 对象的 `ThreadLocalMap` 中，而不是保存在 `ThreadLocal` 本身。`ThreadLocal` 只是一个工具人，提供对线程本地变量的访问接口。

---

**threadlocal 内存泄漏问题？（高）**

**问题根源**
`ThreadLocalMap` 的 `Entry` 使用 `WeakReference<ThreadLocal<?>>` 作为键。这意味着当外部对 `ThreadLocal` 实例的强引用消失后，GC 会回收该 `ThreadLocal` 对象，导致 `Entry` 的键变为 `null`。此时，`Entry` 中的 value 却依然存在，而且因为线程还存活着，`ThreadLocalMap` 持有对 value 的强引用，导致 value 无法被回收，从而发生内存泄漏。

**为什么用弱引用？**
目的是：当 `ThreadLocal` 实例已经失去外部强引用时，允许 GC 回收它，避免 `ThreadLocal` 对象本身无法被回收。但 value 仍然存在，需要额外处理。

**如何解决？**
- **主动调用 `remove()`**：使用完毕后，务必调用 `ThreadLocal.remove()` 清除 Entry，这是最彻底的办法。
- **`ThreadLocalMap` 的自动清理**：在 `get`、`set`、`remove` 等方法调用时，`ThreadLocalMap` 会顺便检查键为 `null` 的过期 Entry，并进行清理（`expungeStaleEntry`）。但这种惰性清理并不及时，无法完全避免泄漏。
- **线程池场景**：在线程复用的线程池中，线程长期存活，`ThreadLocal` 如果不用且没有 `remove()`，value 会一直累积，内存泄漏风险更大。因此必须在使用后执行 `remove()`。

---

**为什么要清除掉 threadlocal？(高)**

1. **防止内存泄漏**
   如上面所述，在线程长期存活的场景（尤其是线程池），如果不调用 `remove()`，即使 `ThreadLocal` 对象本身被 GC 回收了，`ThreadLocalMap` 中的 value 依然被线程强引用，造成内存泄漏。

2. **避免数据混淆（脏数据）**
   在线程池环境中，线程被复用。如果上一个任务使用了 `ThreadLocal` 但没有清除，下一个任务被同一个线程执行时，可能会读取到上一个任务残留的上下文数据，导致业务逻辑错误。例如，上一个请求的用户信息残留到下一个请求中。

3. **资源及时释放**
   有些 `ThreadLocal` 中存放的是需要关闭的资源（如数据库连接、文件流），及时 `remove()` 可以确保资源被回收或归还，避免资源耗尽。

4. **保持内存整洁**
   即使线程最终结束，`ThreadLocalMap` 会随线程销毁而被回收，但线程存活期间积累的无用 `Entry` 会占用内存，增加 GC 压力。主动清除能维持内存高效使用。

---

**ThreadLocal 与 synchronized 的不同之处（高）**

| 对比项           | ThreadLocal                                                  | synchronized                                                 |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **解决思路**     | 用空间换时间，为每个线程提供独立副本，避免共享，从而无需同步 | 用时间换空间，多个线程排队串行访问共享变量，保证数据一致性   |
| **线程安全实现** | 数据隔离，每个线程操作自己的变量，天然线程安全               | 通过互斥锁保证共享变量在同一时刻只有一个线程访问             |
| **性能**         | 无锁，没有上下文切换和阻塞，并发性能极高                     | 有锁竞争，存在上下文切换、线程阻塞/唤醒开销，性能相对较低    |
| **数据关联性**   | 线程与数据一对一绑定，各线程数据相互独立                     | 多个线程共享同一份数据                                       |
| **适用场景**     | 每个线程需要自己独立的实例（如 SimpleDateFormat）、全局上下文传递（如当前用户信息） | 多线程需要对共享资源进行互斥访问、保证原子性操作（如库存扣减） |
